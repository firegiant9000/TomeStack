# Changelog

## Unreleased

### Added
- **Theme presets and a custom accent (item 26, D40):** Settings > Theme now offers three more presets, **Ember** (rust and slate blue), **Rose** (berry and green) and **Tide** (teal and coral), each in light and dark with the contrast of the existing themes (text on a filled shape is `--bg`, 6.1:1 or better), and **Custom accent**: pick a hue 0 to 359 on a labelled slider (the value reads as a colour word and a number, for example "Teal, 180 degrees"), with a live sample. The app moves only the lightness of the colour, in code, until text, the focus outline and filled shapes keep their contrast in light and dark at every hue. Windows High Contrast and printing still win over every theme.

- **Experience points (item 27, R162, R177):** Stats has an "Experience points" section with a "Track XP" checkbox. XP is off by default; ticking it starts a total of 0 and shows a number field (a whole number from 0 to 1,000,000, saved with "Save experience points"), and unticking it drops the total. When the total reaches the next level's threshold the section says "Level up available", with "Next level at 2,700" beside it. This is display only: TomeStack never changes your level or classes, and milestone levelling is untouched. The thresholds (0, 300, 900, 2,700 and on to 355,000 for level 20) are one shared rules constant, `Advancement.XpThresholds`, the same for both rules families, and the check uses your total level across classes. The sheet gains `levelUpAvailable` and `xpForNextLevel`, both absent unless XP is tracked (and `xpForNextLevel` absent at level 20). No new character field or schema version, and no new command: the total saves with `character.save`.

- **Companions on Play (item 23, D39):** a "Companions" section with one card per familiar, mount or the like: name, kind, Armor Class, hit points with "Take damage", "Heal", "Set hit points" and "Set temporary hit points", speed, attack lines and a note. It is a player-owned card of free text; TomeStack applies no rules to it, there is no stat-block import, and a rest does not change a companion. You add, edit and remove a companion and its attack lines (up to 10 companions and 5 lines each) in the same section; the definition is saved with the character, so it travels in backups and shares. Current and temporary hit points are play state, written only by the new `character.play` actions `companionDamage` (untyped: temporary hit points first, then hit points, at least 0), `companionHeal` (up to the maximum, temporary untouched) and `companionSetHitPoints` (exact current, and temporary when sent), all with `companionId`, so a save from a stale screen cannot give them back. "Undo last change" puts a companion's hit points back exactly. An attack line rolls through `roll` with the new target `companionAttack { companionId, attackId }` (d20 plus its typed to-hit, or its damage dice) and shows in Last roll as "<companion>: <attack> attack". New refusal codes: `play.companion-unknown`, `play.companion-hit-points-above-maximum`, `roll.companion-unknown`, `roll.companion-attack-unknown`, `roll.companion-attack-no-damage`. No new character field or schema version.
- **Attunement and item charges (item 25, Q13, Q19):** an item that needs attunement (content v10 `item` effect) applies its effects only while an equipped copy is attuned; until then the sheet says it is not attuned. Inventory has an "Attuned" checkbox on equipped entries of attunement items (more than three attuned is a text warning, never a refusal) and, for an item with charges, "3 of 7 charges left" with pips and "Spend a charge: <item>" / "Regain a charge: <item>" buttons on carried and equipped entries alike. You can carry a second copy of an item with charges or attunement; each copy has its own charges and attunement, and any other item is still one entry with a quantity. A rest returns an item's charges by its `recovery`: all of them, or the dice it names, rolled in the rest panel (or typed from the table) and never more than were spent; an item with no recovery gets nothing back. `character.play` gains `spendCharge` and `regainCharge` (`entryId`, or `entryIndex` with `contentId` for an entry with no id yet), `roll` gains `chargeEntry`, `character.restPreview` and `character.rest` gain `chargeRolls`, and the rest preview gains a `charges` change kind. New refusal codes: `play.entry-unknown`, `play.charges-none-left`, `play.charges-full`, `rest.charge-roll-unknown`, `rest.charge-roll-invalid`, `roll.charges-unknown`, `roll.charges-no-dice`. Saving a character does not change the charges spent of an entry the stored character has (only spending, regaining and resting do), so a slow screen cannot give charges back; an entry whose id the stored character lacks keeps the value it carries, and a save from a stale copy is refused (`character.stale`). Undo takes back a spend or a regain, not a rest. An entry of a charged or attunement item gets an id when it is saved; other entries stay without one. No new character field or schema version; below content v10 the `item` effect still does nothing.
- **Reaction and bonus-action grouping of toggles and resources (item 22, R157):** on Play, a content v10 toggle with an `activation` is listed under that group in "Attacks and actions" (Actions, Bonus actions, Reactions or Other, beside the rolls and attacks of the group), and a resource with an `activation` is listed under the same headings in "Resources". A toggle with no `activation` stays under "Active effects"; resources with no `activation` stay in the plain resource list, shown beside the grouped ones when both exist. An auto toggle ("On while bloodied") keeps its text and has no switch inside its group. The "Active effects" legend now reads "a switch is a confirmed change", which is true when a row has no switch. The sheet carries `activation` on toggle and resource entries for v10 revisions only; below v10 the key stays extension data and does nothing. No schema, package or database change.
- **Damage types: resistance, immunity and vulnerability (item 21, D19 amended):** Play's Hit points panel has a "Damage type" select next to the damage amount ("Untyped" first, then the thirteen types). Typed damage applies the character's defences, from the new "Damage resistances, immunities and vulnerabilities" section on Stats (the list with where each comes from, and a form to record your own) and from content v10 damage grants: immunity takes 0; otherwise resistance halves (rounding down) and then vulnerability doubles; then temporary hit points absorb it; then hit points. Several sources of one kind count once, and untyped damage ignores all of them. The result reads "13 slashing, halved: 6." The concentration save DC now uses the damage after defences (before temporary hit points). Damage that is 0 after defences changes nothing. Massive damage is a warning (`play.massive-damage`), never an automatic death. A weapon's damage roll pre-fills the type when it names one of the thirteen. Undo says "damage 13 slashing (6 taken)" and puts the exact hit points back. `character.play` refuses an unknown `damageType` with `play.damage-type-unknown`. Damage grants honour `level` and `onlyAs`; below content v10 they still do nothing. No new schema, package or database change.
- **Bloodied chip and auto toggles (item 20, D38):** the summary's Hit points box shows the word "Bloodied" while current hit points are at or below half the maximum, rounded down (a maximum of at least 1; temporary hit points do not count; still bloodied at 0), in both rules families. A content v10 toggle with `autoWhen: "bloodied"` switches itself on while the character is bloodied: the sheet works it out from the hit points, it is never stored, never spends a use, has no switch on Play ("On while bloodied") and is left out of the long rest. Switching one by hand is refused (`toggle.automatic`), and a stored toggle naming it does nothing. A homebrew auto toggle that names a resource (`validate.toggle-auto-resource`) or has a modifier on hit points or an ability (`validate.toggle-auto-target`) cannot be published. Below v10 `autoWhen` still does nothing.
- **Content schema v10, defined whole (item 24, D42):** a content revision can now carry damage resistance, immunity and vulnerability grants (`damageType` a damage type), a toggle's `autoWhen` (`bloodied`) and `activation`, a resource's `activation`, an `item` effect (`requiresAttunement`, and `charges` of 1 to 99 with a rest `recovery`), and `speed` and `passive.perception`, `passive.insight` and `passive.investigation` as modifier and restriction targets (not grant targets). The schema is `docs/schemas/content-revision.v10.schema.json`. A revision at v9 or lower that carries any of these keeps its exact bytes and hash and the key has no effect. New validation codes: `validate.requires-v10`, `validate.item-incomplete`, `validate.item-kind`, `validate.item-charges`, `validate.item-duplicate`, `validate.grant-damage-type`, `validate.grant-damage-type-kind`, `validate.grant-damage-fields` and `validate.effect-malformed` (an error in a v10 revision: a toggle, resource or grant whose activation, autoWhen or grant kind is not an allowed name, so it would otherwise publish at a lower version and read back as something else). The entries above use them on the sheet and Play.
- **Import a character from a PDF with no form fields (item 19b, D37, ADR-013):** "Import a character (sheet or text)…" now also takes a printed or flattened PDF. When the PDF has no form fields, its page text (the first 20 pages, with Windows text recognition for a page with no text when it is installed) is read as the text importer reads pasted notes, into the same steps, with the layout named "text from the PDF" and every line that was not understood listed. The text limits apply (262,144 characters, 5,000 lines, 2 seconds); pages after the first 20 are counted in the report, and a PDF with almost no text (a blank page or a scan that could not be recognised) is refused with counts only (`ddb.pdf-no-text`). Pages with no readable text and pages that could not be read are counted in the report. The PDF is opened by the worker twice (the form reader, then the text read when it has no fields) and is not kept. A path must be a full path to a `.pdf` on a local drive: a stream name (`file.txt:name.pdf`) or a device name such as `CON` is refused (`pdf.path-not-local`), and the worker's error text is never shown as sent.
- **Import a character from text (item 19a, D37, ADR-017):** step 1 gains "Import a character from text…": paste text, or choose a .txt or .md file, and it is read into the same steps as a PDF (rules, matches, numbers, summary). Labelled lines (Name, Class and level, Race or Species, Background, ability scores, saves, skills, hit points, armor class, speed, coins, hit dice), lists (spells, equipment, feats, features, languages, tools) and simple Markdown headings, bullets and bold are read; equipment becomes your own items, feats and features without a match become reference drafts, and a class TomeStack does not have can be created from a Hit Dice line. Every line that was not understood is listed as plain text with its line number, and "Keep the lines that were not read as session notes" (on by default) puts them in session notes titled "Not read from the text", which share packages never carry. Limits: 262,144 characters, 5,000 lines, a 2,000-character line is listed but not read, and 2 seconds; a refusal names counts only and nothing of the text. A file over the limit is refused by its size before it is read. The text itself isn't kept; the lines that could not be read become session notes if you keep that tick, and then they are in your backups.
- **Reference drafts for unmatched feats and features (item 16, D16(c)):** a feat or feature on an imported sheet that TomeStack does not have, and that carries text, becomes a reference draft (its name and description, no mechanics) in the same never-shared source as a created class. The summary lists them, with "Publish these N reference drafts" unticked; ticking it publishes them with the character and pins the feats (features are kept in the studio only). Texts are cut at 20,000 characters and at most 100 drafts are made per import; the gap notes stay for every unmatched entry. An entry that source already holds (draft or published) is not drafted again, so importing a sheet twice adds nothing, and publishing is refused if the drafts changed since the summary showed them.
- **Create a homebrew class from a sheet (item 15, D35):** when an imported sheet names a class TomeStack does not have, the Matches step offers to create a minimal one (hit die and saving throws) for this character. It stays a draft unless you tick "Publish it", and it lives in a source that is never shared.
- **Import the fillable 2014 character sheet (item 14, Q14, D16(e)):** "Import a character (sheet or text)…" (renamed from "Import from D&D Beyond PDF…", then "Import a character sheet (PDF)…" until the text importer arrived) now also reads the fillable 2014 sheet, recognised by its field names, with the same steps and the layout named in step 1 and the report. It brings over the name, class and level, species, background, ability scores, saving throw and skill marks and numbers, armour class, initiative, speed, hit points, passive Perception, coins, current and temporary hit points, the death-save boxes and spent hit dice (the last three with "Bring over current hit points…"). Weapon rows become your own attacks (the bonus, the dice and the damage type are read separately; a part that does not read is left empty and said so), equipment lines become your own items, languages and tools fill the Details lists, and alignment and appearance fill Details. Personality, ideals, bonds, flaws, backstory, features and traits, feats and traits and treasure become dated session notes, split into parts when long, so share packages never carry them; what did not fit or parse is kept in one "Import note". Long text boxes are cut at 20,000 characters, with a report line naming the box. The score and modifier boxes are read the way the owner's own sheet fills them (the form names them the other way round from their labels); a sheet filled the other way is still read correctly, with a report line, and a lone score box, or a lone value of 11 to 30 in the modifier box, is read as the score. A ticked death-save box adds a line asking you to check the order, which could not be confirmed, when you bring over the play state (the boxes are not read into the character otherwise). The summary step names the layout it read, and the file picker and the no-form message no longer name D&D Beyond. A file carrying two layouts' field names is refused. The player name, allies, experience points, spells and senses are not brought over.
- **Your own items and attacks (item 18, D42):**
  - Inventory gains "Your own items" (name, quantity 1 to 9,999, a note, an "equipped" reminder; up to 50) and "Your own attacks" (name, a to-hit bonus of −20 to +30, damage dice, a damage type, a note; up to 30), each with add, edit and remove (no confirmation). Custom items never count toward Armor Class or any calculation, and Inventory says so. Bad damage shows the dice engine's own message beside the box (a flat "5" is refused) and saves nothing.
  - On Play, "Attacks and actions" lists each custom attack with "Roll {name} attack" (d20 plus the typed bonus, under the advantage / disadvantage choice) and, when it has damage, "Roll {name} damage" (the "Critical hit" box doubles the dice). The roll record is labelled with the attack's name and cites no content. The panel now shows for a character who has only custom attacks. The `roll` command takes `customAttack` (refusals `roll.custom-attack-unknown` and `roll.custom-attack-no-damage` never quote the name).
  - The Advantage / Disadvantage choice on Play now also applies to weapon and spell attack rolls (it already applied to checks and saves); damage rolls stay normal.
  - Edits are saved with the character and are not undoable (Undo covers play changes only); the roll log is not stored.
- **Character details on Notes, languages and tools on Stats (item 17, D36):** Notes gains a "Details" form after the session and gap notes, with Personality (alignment, personality traits, ideals, bonds, flaws), Appearance (age, height, weight, eyes, skin, hair), Background story (backstory, allies and organisations) and Languages and tools (two lists, one entry per line). "Save details" is held with its reason until something changed and every field fits (a text of at most 2,000 characters; at most 30 list entries of at most 80); a text that is too long, or a list line that is, is a linked error and is never cut. Stats lists the languages and tools read-only, with "Edit in Notes → Details". The print preview has its own "Include details" tick, off by default. A share package keeps the details and still leaves the session notes out; the sheet JSON and Foundry exports carry none. A snapshot restore preview names the detail fields it would change (never their text).
- **Accept many candidates at once:** in the import review, tick rows (or "Select the 50 shown") and choose "Accept selected as drafts" or "Accept selected as reference". Each goes through the same checks as accepting one; the ones that need review are listed with the reason and stay selected, and nothing is forced.
- **Publish all drafts in a source:** the Homebrew studio's "Publish all drafts in this source…" shows what will be published (problems, what replaces a published version, which grants are re-pointed at the published features) and publishes the ticked drafts in one all-or-nothing step. A repeat press publishes nothing twice, and if a dependent it showed was added, removed or republished since the check, the publish is refused and checks again. The check runs after a short pause in ticking, there is one "Tick all" / "Untick all" button, no more than 500 drafts are ticked to begin with, and a refused publish checks again with a fresh list. A screen reader hears one summary per check ("No problems; 3 drafts ready.").
- **Spell lists for imported spells:** "Add to a spell list…" puts a list key (for example `wizard`) on the ticked spell candidates in the import review, before you accept them, and on selected spells in the Homebrew studio, where it saves new drafts (never publishes) and opens "Publish all drafts" on exactly those. The key box offers the lists already in use with their spell counts and shows the key as it will be saved. The PDF import also reads a "<Name> Spells" list page and proposes its key for the spells it names (marked unsure; a list carries over a page break). Adding a key the import proposed confirms it, while other proposed keys stay marked for review. A spell with an unpublished draft is skipped in the studio until that draft is published or discarded. The `validate.spell-lists` warning now says what to do. Characters keep the spell revisions they recorded until you review an update for each one.
- **Species, backgrounds and spells in the Homebrew studio:** "New species", "New background" and "New spell" sit beside "New class". A species has ability increases, skill proficiencies and traits (pick an existing feature or make one with "New feature"). A background has skills and, as the rules family says, either a feature (older rules) or a feat plus three picked ability increases (newer rules, saved as seven option features that the background pins). A spell has level, school, ritual, concentration, casting time, range, components, duration, text and spell lists (the list box shares the key checks of "Add to a spell list…"). A background with ability increases points at its option drafts; a note beside Publish says so and that "Publish all drafts in this source…" publishes them together and re-points it (Publish itself is not held; "Publish all drafts" waits while the open editor has unsaved changes, and a clean editor left open on an entry that "Publish all" published closes with a status). A pin at a superseded draft offers "Use the published version" instead of re-pointing silently, a rename keeps the choice and option ids, and a species' increases are 1 to 9. A species can set its speed (a "Speed (feet)" field, 5 to 120, optional): it is saved as a content v10 `replace` modifier on speed, so a feat's speed bonus still adds on top, and publishing such a species needs content v10 (older builds refuse it). Bundled species still carry no speed (30 feet by rules policy).
- **A detected class ends in a usable class draft:** the PDF import rebuilds the class table (level, proficiency bonus, features, and for a caster the cantrips, spells and slot columns, or a pact table) and proposes the hit die, saving throws, armor and weapon proficiencies, a subclass choice and, for a caster, spellcasting. Traits are read with or without a colon and from two-column trait boxes; a weapon line with a condition, and any missing saves, armor or weapons, are said as uncertainties instead of guessed; skills are shown with an uncertainty for you to add in the studio. The review shows the slot table with "Open page" beside it and every feature the class links, saying which are installed, already accepted or ignored. Each proposal has its own "Confirm …" tick; "Accept as a draft" is held until the hit die and, for a caster, the spell slot table are ticked, only what you ticked stays automatic, and saving an edit that changes the effects clears the ticks. The linked features are saved as drafts first, in the same step, and the class pins them (an accepted one at its newest published version), so the class and its features publish together. A feature the table names that was not found on its own page becomes a reference stub (one per class, never shared; a same-name feature is linked only when it belongs to that class), so feature counts in a book rise; renaming a linked feature keeps its link; a name that matches exactly one installed feature is pinned to it instead; an ignored linked feature is left out, not a blocker; a table feature that has neither a link nor a single installed match when you accept is counted in a note and not granted; the status after accepting says "granting N features"; trait-box reading takes the labelled lines on the page that carries the "Core ... Traits" heading, so a page with two trait boxes needs your ticks; and one reviewed in an earlier import of the same PDF is counted in an uncertainty. Nothing is active until you publish (ADR-016).
- **A session-prep guide** (`docs/features/session-prep.md`) for characters built mostly from homebrew.
- **Roll any dice from the summary:** type something like 2d6+3 under the d20 mode and choose Roll dice. The result shows under Last roll like any other roll; nothing is saved.

### Changed

- **The app starts with less to load (R161):** the Homebrew studio, sources, the character builder, the sheet importer, campaigns, backups, extensions and the package preview now load when you open them, and the page says "Loading…" while one does. Nothing else changes; the app still works offline.
- **PDFs on network shares can no longer be attached or imported:** a PDF you choose to attach, link or import as a character sheet must be a file on a local drive (a full path with a drive letter, no network share, device path or `..`). Otherwise it is refused (`pdf.path-not-local`) before anything opens it, because Windows would connect to the other computer just to read the file. Copy the file to this computer first. A drive letter you mapped to a share is not detected.
- **One importer entry for every character sheet PDF:** the sidebar button, the step title, the file input's name and the status after creating read "character sheet" instead of "D&D Beyond". "D&D Beyond" now appears in the layout's name ("D&D Beyond 2014"), the not-affiliated line, and, for a D&D Beyond sheet, the override reason and note text written into the character. A PDF with no known layout is refused with "do not match a known character sheet layout".
- **A caster without spell slots says so:** spellcasting is proposed only from a class table's spell slot columns. When a class's table has none but its text mentions spellcasting, the class candidate now says "add spellcasting by hand if it casts spells", so it no longer imports silently with no spellcasting.
- **Better at third-party books:** the PDF import now finds feats whose name and prerequisites share a block, spell, feat and class names printed in capitals (shown in title case), and class tables titled in capitals, and it no longer proposes table rows that are prices or sentence fragments. Measured on the SRDs (no drop) and on a third-party book (counts in m4-acceptance.md).
- **The builder says why a class, species or background is missing:** it counts entries that are still drafts in the Homebrew studio, and entries written only for the other rules family, without naming them.
- **The import review says what happens next:** a line above the candidates says that accepted entries are drafts in the Homebrew studio, and a button opens that source in the studio.
- **Reading a two-family book asks "This book is written for":** 2014 rules, 2024 rules or both, with no default. The Read buttons wait for the answer and say why. A job stores the answer (`writtenFor`, optional; a 0.5.0 job without it uses the source's families).

- **The candidate list pages through long books** (50 at a time), filters by a page range, and says when detection stopped early. While you have an unsaved edit open, the paging buttons, the filters and the other candidates are held with "Save or undo your edit first."; choosing another candidate used to drop the edit silently.

- **Saving a character that changed elsewhere is refused and the current copy is shown** (R161, R182). `character.save` compares the `updatedAt` it carries with the stored one and refuses a mismatch with `character.stale`, writing nothing. The sheet shows the refusal, reads the current copy and keeps focus where it was. A new entry that takes the place of a removed copy of the same item now starts with full charges, and the earlier id pairing for stale copies is gone (a stale copy is refused instead). Details in `features/sheet-play.md` and `features/equipment.md`.

- **A screen whose code cannot load says so** ("This screen couldn't be loaded.") and the navigation stays usable, instead of a blank window.

### Fixed

- **Wave 3 whole-branch review fixes:** a character that already holds two copies of an item (for example from a share whose source did not arrive, or after an update that dropped the item's charges) can still save and take play and rest actions; the "one entry per item" rule is checked only for copies a save adds (R184). A companion's "Set temporary hit points" no longer writes back the hit points the screen showed, so a damage that landed a moment earlier is kept (new `character.play` action `companionSetTemporaryHitPoints`). The companion buttons now point at "Enter an amount first." while the amount is blank. "Add" in the damage defences list stays focusable when the pair is already recorded. A charge roll that went stale during a rest can be cleared. The restore preview notices a change in a second copy of an item. A pinned item that needs attunement is held to the same attunement rule as an equipped one. The messages for `validate.item-kind`, `validate.effect-unsupported`, `item.not-attuned` and `rest.recover-by-hand` no longer quote content names. Item uses are worked out once per sheet instead of once per pass.
- **A slow search while finding entries is retried once (R161):** if a search takes longer than 1 second, the importer finds entries once more, and only a second timeout fails the import with `detect.timeout`. The pages stay searchable either way.
- **Test fixtures and notes no longer carry book item and feature names (R152, R149):** the importer tests use invented names; the one reference-only feature name the detector skips is a single named constant (R181). No behaviour change.
- **The worker page-timeout tests no longer race (R173):** they now run against a stand-in worker that sends nothing, so a fast computer cannot answer before the timeout fires (test-only change).
- **The mechanics report no longer lists scale values as unsupported (G3):** a per-level scale (`SCALE.<id>`) and an item's charges are known effect types, so the report counts them as automatic instead of flagging them as gaps.
- **An import no longer fails with "took too long" on a busy computer (R151):** each search the importer runs to find entries may now take up to 1 second. Some searches cover a whole block or page of text. The limit was 0.1 s, which a busy computer could exceed on any search. A pattern that runs longer still stops the import with `detect.timeout`.
- **A change refused because the item or spell is gone is announced as a status, not an error (R144):** toggling Equip on an item, or Prepared on a spell, that was removed meanwhile (by a restore, an import or another panel) saves nothing and says so in the polite status line, as the custom items and attacks already did. Focus stays on the control.
- **The local-path check also refuses the console and superscript device names (R116):** a file named `CONIN$`, `CONOUT$`, `COM¹`, `COM²`, `COM³`, `LPT¹`, `LPT²` or `LPT³` (any case, with or without an extension, in any folder of the path) is refused like `CON` or `COM1` already were.
- **A page with many class headings is read in bounded time, and Cancel stops it (R127):** the per-page class split now splits at most 8 class titles; a page with more is read whole, as before the split existed. Each window is read once (a window that did not change after a class was dropped is not read again), and the split, and the reading of each class table (the whole-table reader and the older header scan), check for Cancel as they go.
- **The importer's entry names both ways in (R133):** the sidebar button and the import's title read "Import a character (sheet or text)…" (they said "character sheet (PDF)" even though a text entry sat inside), and step 1's first line names a fillable sheet PDF, or pasted text or a .txt or .md file. The text importer's hint no longer says the text is "read once and not kept": the text itself isn't kept, but the lines that could not be read become session notes if you keep that tick (R131).
- **Text import counts spells past the list limit:** a spell list over 1,000 entries used to drop the extra spells after one placeholder with no word about it. The report now says how many spells were beyond the limit and were not read (a number, never a name), as it already did for feats and features.
- **Long import reviews and publish previews are quicker (R82):** a page of candidates is read with a query on the new columns instead of loading every candidate of the job (the index covers the page-turn query), and the "Publish all drafts" check no longer blocks other actions while it plans: the database lock is held only for its dry run. The preview itself is not faster.
- **A book's armour and class tables no longer default to the 2024 rules:** when a source is written for both families, TomeStack asks what the book is written for when you read it, and an entry it cannot place waits for you to choose its family. You can now change a candidate's rules families in review (only to families the source declares). Pending candidates that 0.5.0 already found stay in the old reading's list and now ask for a family too, until you save one (also when you edited them in 0.5.0, which never asked); reading the document again makes a new list. An entry already accepted from another reading of the same document is not accepted a second time.

- **Saving a candidate edit no longer overwrites a newer one (R120):** the edit now carries the candidate's last-seen state (`etag`, a SHA-256 of the stored row, returned with every candidate). If the candidate changed since the editor opened (another save, a spell list added, a re-read), the save is refused (`import.candidate-changed`), nothing is written, and the review reloads the candidate and says "This candidate changed since you opened it. It has been reloaded." The check and the write share one transaction. `StoredCandidate` also types `familiesReviewed` in the UI.
- **Class import reads each class from its own part of the page (Wave 0/1 minors):** the "Core … Traits" lines are read only from that heading's block, so one class no longer picks up another's saves and proficiencies. Two classes on one page are now two class candidates, each read from its own window, with a reference stub of its own for a shared feature name; a feature printed on that shared page is linked to neither, and the pages after it belong to the last class. Accepting a class re-reads it inside the same transaction as the write: if it was edited meanwhile it is refused (`import.candidate-changed`), and if it was reviewed meanwhile, refused as already reviewed; nothing is written either way. The SRD link and stub counts for this change are not yet measured (see `features/m4-acceptance.md`).
- **Review fixes to class import and candidate review (Task 8a, Wave 0/1 minors):**
  - Two classes on one page that list one feature name keep a stub each when you review one and read the document again (or read it a second time): reviewing one stub no longer hides the other, retargets the other class's link to it, or gives a false "reviewed in an earlier import" note or `import.already-accepted`.
  - Accepting a class is refused (`candidate.linked-edited`, its own code and message; not `import.candidate-changed`, because the class itself did not change) when a feature it grants was edited while the accept ran, instead of saving that feature from the old row and losing the edit. The review panel then fetches the class's check again and says so (it used to show the refusal as an error and keep the stale check, as the class's own etag had not moved).
  - Ignoring a candidate re-checks inside the transaction: if it was edited or accepted meanwhile, the ignore is refused (`import.candidate-changed` or `candidate.already-reviewed`) and nothing is overwritten. Accept, accept-many and ignore return the row as stored, with its new `etag`. A refused accept or ignore says "Review it again" (not "edit again"), and the review panel reloads the candidate and says it changed, as it does for an edit.
  - Accept, accept-many and ignore now send the candidate's last-seen `etag` (accept-many one per id) and check it before and inside the transaction, as an edit does (R134). Before, they compared against the service's own read, so an edit made between the panel's read and the press went through. A missing or stale token is refused (`import.candidate-changed`), and one stale row refuses the whole accept-many with nothing written. The review panel then reloads the list, clears the selection and says "Some selected candidates changed; the selection was cleared." (before, it kept the stale tokens, so every retry was refused).
  - Accept as a draft, Accept as reference and Ignore are held, with "Save or undo your edit first." linked as their reason, while the open candidate's form has an unsaved edit (R134). They used to act on the stored candidate and leave the edit on screen, as if it had been part of the accept.
  - "Add to a spell list…" returns the candidates as stored after the write, with their new `etag`, like accept and ignore (it returned the row from before the write, whose `etag` the next edit or accept would then be refused for).
  - The character import's preview describes the character it saves (R129). A created class counts in the preview's numbers (hit points, saves, the comparison, overrides and gap notes) only when "Publish it" is ticked; unticked, a number that relies on the class shows as differing, as it will on the saved character. Ticking or clearing "Publish it" fetches a new preview, and while that preview is loading, "Publish it" and the reference tick are held with the reason linked (they were not held before); after a failed preview they are free again and "Create character" stays held, and the reason has a fixed place beside each tick so it does not shift the tick (R142). An apply whose publish choice differs from the previewed one is refused (`ddb.publish-changed`) and writes nothing. The screen sends the choice of the preview it is showing (not of its current request), and the service requires it whenever the sheet offers a class: a missing value is refused too (R141).
  - The restore preview names every v9 value a restore brings back (R128). Besides details, it now says when your own items, your own attacks, or experience points, damage resistances, companions, and the attunement and charges spent on equipment would go back to the snapshot (`customItemsChange`, `customAttacksChange`, `otherSheetValuesChange`; flags, never the names). Before, a restore replaced them without a word.
  - Two sheet panels saving close together no longer overwrite each other (R92, R132). Each panel used to save a copy of the character it had loaded, so a second save sent the first panel's field back at its old value. Every sheet save (equipment, coins, your own items and attacks, details, session notes, prepared spells, overrides) now goes through one queue in the sheet: the panel's change is applied to the latest saved character and the saves run one after another. Each panel keeps its own status and focus. A snapshot restore or applied update that is shown while saves are queued is kept by the queued saves. `character.save` is now compare-and-set (see the Changed entry and `features/sheet-play.md`). An equipped or prepared toggle is worked out from the latest saved list, and an edit, equip or prepare for an entry that was removed meanwhile is refused with its own message (it used to be dropped under "Saved").
  - The character import's header line no longer says "The PDF is read once and not kept" on every step, text imports included (R131). It names the source: "The PDF itself isn't kept." or "The text itself isn't kept." (the worker opens a PDF twice when it has no form fields, so "read once" was never true). The source is how you chose the sheet (a PDF, or pasted or file text), not the layout it was read with, so a PDF without form fields is still called a PDF; step 1 and the client comments no longer say "once" (R143).
  - The version is 0.6.0 on this branch (`Directory.Build.props`, R130), as the migration text already says. Builds now stamp `0.6.0`, and opening a 0.5.0 folder leaves `tomestack.db.app-pre-0.6.0-to-0.6.0.bak` next to `tomestack.db.v10.bak`, both the database as 0.5.0 left it. Before, a branch build stamped `0.5.0` and named the copy `app-pre-0.5.0-to-0.5.0`, and a later 0.6.0 copy would have held version 11 data. A data folder opened by a branch build from before this change is stamped `0.5.0`, so the next start leaves `tomestack.db.app-0.5.0-to-0.6.0.bak`, which holds version 11 data (not a 0.5.0 database); `tomestack.db.v10.bak` is the one to go back to. Tagging and releasing stay the owner's.
  - The one-time upgrade that fills the new candidate columns skips any row it cannot read and no longer stops the data folder from opening. The upgrade's index (still the unreleased v11) now covers the page-turn query.

### Migration

- **Content schema v10** is not an upcast. A build older than v10 refuses a v10 revision, and a package holding one, with `content.schema-unsupported` (`package.schema-unsupported` for a package). `content.publish` writes the lowest version a revision needs, so content using none of the additions still publishes at v9 or lower and stays readable by 0.5.0 and the Wave 2 build. "Edit as new draft" on an older revision reads the copy with the current schema (it sends no schema version), so any v10 key the old revision carried takes effect in the new draft (validation shows it); the stored revision is unchanged.
- **Database version 11 (back up first):** the candidate list now filters and pages in the database, so `import_candidates` gains indexed columns (`kind`, `page`, `page_end`, `name`, `confidence`) filled from each stored candidate when 0.6.0 first opens the folder. The stored candidate itself is not changed and stays the source of truth. Once 0.6.0 opens a data folder, **0.5.0 cannot open it**; back up the data folder first. TomeStack also copies the database before the change (`tomestack.db.v10.bak`, plus the one-time app-version copy below).
- **Character schema v9** (`docs/schemas/character.v9.schema.json`) adds `details`, `customItems`, `customAttacks`, `damageDefences`, `companions`, `xp`, an equipment entry's `id`, `attuned` and `chargesSpent`, and `play.companions`. A character is written as v9 only when one of them is set; otherwise it is written as v8, byte for byte as 0.5.0 wrote it, in the database, a character package, a library backup and a snapshot, so a character you never touch with the new fields still opens in 0.5.0. 0.5.0 refuses a character that has any of them (`character.schema-unsupported` on save, `package.schema-unsupported` on import); the package format is unchanged. The database moves to version 11 (see the bullet above), so 0.5.0 cannot open the folder; characters written as v8 stay readable by 0.5.0 in packages and backups. Removing the last v9 value makes the character v8 again on its next save. The service checks the new fields with bounds of its own (text up to 2,000 characters, at most 50 custom items and 30 custom attacks, 10 companions with 5 attacks each, to-hit from -20 to +30, XP up to 1,000,000), and the 5 MB limit on one backup entry still applies, so every character that saves also backs up.
- **A one-time copy of the database when a new version first opens your data folder:** the data folder now holds `tomestack.app-version` (the version that last opened it). The first time a newer version opens a folder that an older one used, it copies the database to `tomestack.db.app-<from>-to-<to>.bak` (`<from>` is the version being left and `<to>` the version opening it, for example `tomestack.db.app-0.5.0-to-0.6.0.bak`; a folder from 0.5.0 or older has no stamp, so `<from>` is `pre-<this version>`, as in `tomestack.db.app-pre-0.6.0-to-0.6.0.bak`) before anything changes, so you can go back to the build you came from. If an exact copy for that pair already exists (a launch that failed and was retried), it is kept, not overwritten; if the stamp cannot be updated, the error is logged and the next version still gets its own copy. A new folder gets the stamp and no copy; a folder stamped by a newer version gets no copy and is not touched. These copies sit beside `tomestack.db` (for the installed app, in `%LOCALAPPDATA%\TomeStack`), are never deleted by TomeStack and may be deleted by hand once you are happy with the new version. They are separate from the `tomestack.db.v<N>.bak` copy taken before a database migration.
- A stored class candidate may carry `grantsCandidates` (the feature candidates it links and their levels; omitted when empty; 0.5.0 ignores it and keeps it when it saves the row). `import.candidate.accept` takes an optional `confirmedEffectIds`; a class cannot be accepted as a draft without its hit die confirmed, and `acceptMany` no longer accepts a class as a draft (use Accept on the class, or accept it as reference).
- Import jobs may record what a book is written for (`writtenFor`; 0.5.0 ignores it), and a stored candidate may carry `familiesReviewed` (set when you save a family; absent otherwise; 0.5.0 does not read it and keeps it unchanged when it saves the row). A candidate this version leaves without a rules family cannot be edited or accepted by 0.5.0; ignore it there or read the document again.
- Import jobs may record `truncatedCandidates` and `detectionLimitedFromPage` (optional, omitted when absent; 0.5.0 ignores them). `import.candidates` now returns `{ items, total }` and takes `offset`, `limit`, `firstPage` and `lastPage`; the app and its service ship together.
- **Custom accent (page storage, no migration):** the theme stays in `tomestack.theme` (`custom` for Custom accent; `ember`, `rose` and `tide` for the presets) and the hue in `tomestack.accentHue` (an integer 0 to 359; anything else reads as the default blue, 265). A build older than this one reads `custom`, `ember`, `rose` and `tide` as unknown, shows forest and ignores the hue key; nothing is lost and nothing needs converting. No package, share, database or schema change.

- **Extensions, without running any code (M6 slice 3, ADR-011; approved by the owner 2026-09-30):** the Extensions screen installs an extension file after showing what it would be allowed to do; you tick each permission it may use, and can turn it off or remove it at any time. An extension is a set of instructions that TomeStack carries out itself, within strict limits. An import (for example a CSV spell list) becomes draft content in a new source that is never shared; an export (for example a Markdown summary of a sheet) leaves out content that may not be shared, keeps every license notice, and is checked for your folder paths and user name before it is saved. Every run shows its result before anything is written. The sample is in `examples/extensions`. Full backups keep installed extensions, which come back turned off with no permission granted.
- **Share a campaign as a campaign pack (M6 slice 2; approved by the owner 2026-09-30):** "Share …" on the Campaigns screen saves the campaign's rules, allowed sources and house rules, with the published content of the homebrew you marked as your own work. The SRD is named, not copied, and every other allowed source is only named, with the reason shown before you save. It never carries characters or gap notes. Importing a pack for a campaign you already have asks whether to keep your version or use the imported one, and lists the characters whose content the imported one would no longer allow. A source the pack only names, and that you do not have, stays allowed and is shown as "waiting" until you install it.
- **Share your own homebrew as a source pack (M6 slice 1; its schema changes approved by the owner 2026-09-29):** on the Sources screen, "Mark as shareable…" asks you to confirm that a source is your own work, and "Share sources as a pack" saves those sources with their published content: no characters, drafts, PDFs or text read from PDFs. Importing a pack shows the sender's statement and copies your library first. From this version on, a source that gets a PDF attached, pages imported or a PDF candidate accepted is marked for good as holding imported material: it is never shared, not in a pack and not in a character share, even after the PDF is removed. Sources from earlier versions are marked if they have a PDF now, had one before database version 3, or have an import job. The data folder moves to database version 8, and full backups to package format 7 (see Migration).
- **Snapshots of a character (M5 slice 8):** "Take snapshot" on the sheet keeps a copy of the character to come back to. "Restore" first shows what would change. It then keeps a snapshot of the current state as well, so every restore can be undone. Snapshots stay on this computer: exports, shares and full backups leave them out. The data folder moves to database version 7; the previous version is backed up first (`tomestack.db.v6.bak`).
- **Design feedback, if you want it (M5 slice 7):** a "Show design feedback" setting in the studio, off by default. When it is on, "Get design hints" compares a class or feature with the SRD classes. It points out more spell slots than any SRD full caster has, a multiclass share that gives more slots than the class's own table, a resource that grows faster than any SRD pool, and levels that give nothing. Hints never block publishing, never change a character and are never exported.
- **Start homebrew from a template (M5 slice 6):** four starting points in the studio: a feature with limited uses, a stance you switch on and off, a subclass skeleton and a class skeleton. A template opens as an unsaved draft; nothing is saved or published until you do it. The skeletons leave empty feature slots at the usual levels, which you fill with your own published features. The studio can now also edit toggles, and bonuses that apply only while a toggle is on.
- **See how your homebrew fits together (M5 slice 5):** "Show relationships" in the studio editor draws a tree. For a class it runs by level, through the features and choices it brings in, to the resources and to the rolls and rests that use them. It also shows what never applies, such as a grant inside granted content. It works fully by keyboard and with screen readers, and Enter on a rule jumps to it in the editor.
- **Compare two versions of your homebrew (M5 slice 4):** "Compare revisions" in the studio editor shows what changed between any two versions, including the unsaved one on screen. It shows the rules and the texts line by line, and what each version would give copies of your characters (and a blank character, for a class or subclass). Nothing is changed. The update review uses the same calculation.
- **Try a class or subclass before you publish it (M5 slice 3):** "Try it" in the class and subclass editors shows how the revision on screen plays, at a level you pick. It runs on a blank character or on a copy of one of yours, with the calculated sheet fields it would change. Nothing is saved, and your characters keep using published content only.
- **Find problems in your homebrew (M5 slice 2):** "Find problems in <source>" in the homebrew studio checks all of a source's content, drafts included, and "Find problems" checks the entry you are editing. It finds what the Check button cannot see on one entry alone. Examples: a resource nothing spends or recovers, a recovery or action for a resource that isn't there, a grant that never applies because the content is itself granted, a subclass no class offers, a class feature nothing grants, a choice with nothing to pick, class columns that are read but missing or defined twice, and grants of an older version. **Show** opens the entry and moves focus to the rule. Nothing is changed.
- **Write your own class in the homebrew studio (M5 slice 1b; ADR-010):** "New class" sets the hit die, the saving throws and multiclass prerequisites. It can also set:
  - a skill choice (TomeStack creates the skill options for you);
  - a subclass choice at any level, which your own subclasses join;
  - class columns such as "Ink", which resources and other formulas can read;
  - features by level;
  - spellcasting with its own slot table and a caster share for multiclassing.
  
  The class appears in the builder like any other, and the sheet shows its columns under "Class columns". Content that uses these features can only be opened by this version of TomeStack or later.
- **Classes with their own columns and caster shares (M5 slice 1a; ADR-010; rules engine only):** class content can now carry named per-level columns, such as "Ink: 2, 2, 3 …". Its formulas can read them, so a resource, a roll bonus, a skill or a prepared-spell count grows with the class. A caster can also say exactly how many caster levels it adds at each class level, for example two thirds, and it combines with the SRD casters on the Multiclass Spellcaster table. The homebrew studio cannot author these yet; that is the next slice. Tested on an original fixture class, not bundled content.

- **Archive a character (SPEC C-08, audit 2026-09-28):** "Archive…" on the sheet first says what happens, then moves the character to a collapsed "Archived" list after you confirm. Nothing is deleted: its play state, gap notes, campaign and the content it uses all stay, and "Back up everything" includes it and restores it archived. "Unarchive" brings it back as it was. There is no hard delete. Exporting a character never passes on that it is archived, and importing a package never archives or unarchives one. Older versions of TomeStack show an archived character as active.

- **The Fighter and the armor table (M2.2; `docs/licensing/srd-pack-review.md` "M2.2 extension"):** the SRD Fighter, levels 1–20, in both rules families, with the Champion, and the SRD armor and shield table.
  - **Automated:** Fighting Style as a choice (Defense adds +1 AC while you wear armor), and Second Wind, Action Surge and Indomitable as resources that come back on rests. Second Wind rolls 1d10 plus your Fighter level. Also automated: the number of attacks (Extra Attack) and the Champion's critical range. The Champion's second Fighting Style is a choice too, and a style can't be picked twice.
  - **Armor:** light, medium and heavy armor and shields set Armor Class as before. They now also warn when you lack the Strength (speed 10 feet lower) or the training, and Stealth warns about disadvantage. Under 2024 rules a shield without training adds nothing to Armor Class; under 2014 rules it still does.
  - **Reference text, applied by hand:** the other Fighting Styles, Weapon Mastery (the kinds you choose), Tactical Mind and Tactical Shift, Remarkable Athlete, Heroic Warrior, Survivor and Ability Score Improvements. The feature texts say what to do.
  - **Homebrew:** a homebrew Fighter subclass joins the Fighter's subclass choice next to the Champion, which is the path the Stardust Guardian will take.
  - **Paladin and Ranger:** their Extra Attack is now counted too, and their armor training is recorded (the Paladin's heavy armor only as a starting class), in new revisions. New Wizard and Sorcerer revisions record that they have no armor training. Existing characters get them through "Updates available".
  - **Content schema v8** adds the fields this needs. Older content is unchanged, and older versions of TomeStack refuse v8 content with a clear message. Homebrew you publish is saved in the oldest content version that can hold it, so homebrew that uses none of the new fields can still be shared with TomeStack 0.3.x.

- **Back up everything and restore it (M2.1; `docs/features/package-format.md` "Full library backup", ADR-007 item 10):** a new **Backups** screen.
  - **Back up everything** saves one file with your whole library: characters, campaigns, gap notes, all your homebrew (drafts, older versions and entries no character uses yet) and the PDFs TomeStack keeps a copy of. Before this, only characters and what they used could be backed up, so unfinished homebrew had no backup at all.
  - **Restore full backup** checks the whole file first, PDFs included, shows what it would add or replace, and restores only when you confirm. It deletes nothing. Before it replaces anything, it saves a copy of your current data in the backups folder.

Read some pages or the whole book, watch the progress, cancel or resume, and search the text. Then review the candidates, filtered by page, kind, confidence and status. Each shows its excerpt next to "Open page", what was read, what is unsure, and what it depends on. Edit it, accept it as a draft or as a reference entry, or ignore it. Accepted entries are drafts in the studio, where publishing checks them again.

- **Reviewing candidates (M4 D4; `docs/features/pdf-import.md`):** before a candidate is accepted, TomeStack checks the entry it would become (rules, references, formulas) and shows what it depends on. It stays blocked while a field is unsure or a name it refers to is missing, until you edit it or accept it as a reference entry only. Accepting creates a draft; nothing applies until you publish it in the studio.

- **Candidate detection (M4 D3; `docs/features/pdf-import.md`):** an import proposes candidates found in the book's text: spells, feats, class features, weapon and armor table rows, and class feature tables. Each has its excerpt, page, proposed rules, a confidence and what it is unsure of, and the names it mentions that are not installed. Nothing becomes content until you review it. Measured on the two SRDs: every spell is found with its level, and every bundled weapon and class is found.

- **Import jobs (M4 D2; `docs/features/pdf-import.md`):** extracting a PDF runs as a job you can cancel and resume. It survives closing the app and keeps a local audit log with no text from the book. Extracted text is searchable within its source. Imported text stays on this computer: no backup or share includes it.

- **PDF text extraction (M4 D1, ADR-009; `docs/features/pdf-import.md`):** TomeStack can read the text of a PDF page by page, with its layout, and reads pages without a text layer with Windows' built-in OCR. Nothing is imported yet: import jobs and candidates follow.

Review it to see what changes, then apply it or keep the current revision. Nothing updates by itself.

- **Gap notes follow-ups (M3 C5; `docs/features/gap-notes.md`):**
  - **Report a gap:** a button on every feature and field fills in the gap note's "About" and puts the cursor in the text box.

### Fixed

- **Packages can no longer take over existing content (M6 stack review, 2026-09-30):** a character package that adds a new version of an SRD or homebrew entry under a different source, or splits one entry across two of its sources, is refused (`pack.content-conflict`), as source packs already were. Before, the added version became the one new characters and update offers used. Only versions the package adds count, so your own backup of an entry that an earlier version split across two sources, or the copy saved before an import replaced a character, imports again on the computer that made it. The studio no longer saves a draft of an entry under a different source than the one it has (`content.source-mismatch`). A character that uses SRD content from a newer TomeStack says to update TomeStack instead of calling the content foreign. A package from a later TomeStack that adds a new kind of entry now asks you to update TomeStack instead of calling the file damaged.
- **Campaigns in character shares, and large campaign packs (M6 stack review, 2026-09-30):** a character share now writes its campaign as a campaign pack does, without the list of sources waiting to be installed or properties this version does not know (a backup keeps both). Importing a campaign pack with a very long list of allowed sources no longer freezes TomeStack.
- **Design feedback compares only with the bundled SRD (review of #36, 2026-09-29):** a revision you or a package added under an SRD source, or as a newer version of an SRD feature, no longer becomes the baseline of the hints.
- **No false "multiclass share above table" hint (review of #36):** a class whose own slots skip a spell level (for example none of level 1, six of level 2) is compared by its highest spell level, not by how many levels have slots.
- **Older snapshots stay reachable (review of #36):** the snapshot list shows 100 at a time, and "Show older snapshots" loads the rest, so a snapshot pushed down by many restores can still be restored.
- **The relationship tree no longer treats a draft as granted (review 2026-09-29):** a grant or choice option that names a draft is shown with a note that characters get nothing from it until it is published, and content that extends a choice while a draft is marked as not offered yet.
- **Compare revisions review fixes (2026-09-29):** a huge text that is too long to line up is now cut to a fixed number of lines and characters, and says "N more lines not shown". Compare now shows the problems a version resolves and the choices it leaves open, offers characters by the families of the two versions (and those with a recorded exception), and no longer sends a character you can no longer see.
- **Homebrew debugger review fixes (2026-09-29; `docs/features/homebrew-studio.md`):** reach now follows the exact revision a grant or option names, as the calculator does, and every published revision that extends a choice; the scale problems still show when the walk is cut short; the "granted content's own grants never apply" note no longer hides that a character can pick the content directly.
- **Class editor (M5 slice 1b review):** creating the skill choice again no longer publishes duplicate option features, the whole editor is disabled while it publishes, the rule list shows every multiclass restriction and saving throw grant the editor does not show, and a choice with no listed options can no longer ask for more than 20.
- **Content schema v9 (M5 stack review, 2026-09-29):** a class column (`scale`) written in the wrong shape is refused when you check or publish it, instead of publishing with the column silently missing. Importing a package or restoring a backup no longer refuses revisions that publishing allowed: an inert `scale` in content an earlier build published, and a column id that clashes because of the order things were published, are warnings there.
- **A data folder always opens after an update (full-stack review 2026-09-28):** if your library already holds different content under the id of a revision a new TomeStack version bundles (for example from a package imported earlier), TomeStack now keeps your copy, skips the bundled one and says so at startup. Before, it refused to open the data folder at all, on every launch.
- **Archiving no longer pulls you back:** if you open something else while an archive or unarchive finishes, you stay where you went.

- **Fighter review fixes (M2.2, PR #12 review; `docs/features/equipment.md`, `docs/features/multiclass-and-attacks.md`):**
  - Armor training is checked only when every class the character has levels in records it (and is installed). A Paladin who took a level of Fighter is no longer told they lack training for their plate, and under 2024 rules a Cleric who takes a feat granting light armor keeps the shield's Armor Class. A Wizard who takes a level of Fighter is still warned about heavy armor.
  - A roll's bonus keeps its sign: a Strength 8 bonus is −1, not 0. The button shows it as "1d6 − 1", and the roll record calls it "<roll> bonus" instead of showing the formula. A bonus that cannot be worked out for the character is shown as a problem on the feature, and the roll is refused instead of rolled without it.
  - The critical range stays between 1 and 20, and the number of attacks is at least 1, with a warning when content goes past that. Homebrew can lower the critical range only with a bonus (a "set" or "replace" would keep the highest value, which is the wrong way round), and can't make an Armor Class replacement that applies only in armor (it could never apply).
  - Content that claims an older content version but carries the new Fighter fields (including the attack count and critical range) has those fields ignored, as an older TomeStack would, with a note on the sheet.

- **CI (M2.1):** the UI flow no longer fails at random. Five checks read the status line before it changed and saw the previous message (three failed runs on 2026-09-28). They now wait for the expected text, and lint refuses the old pattern in the e2e tests. A sixth race: the Barbarian flow read the long-rest proposal as soon as the panel had focus, before the proposal had arrived (reproduced by delaying it 400 ms), and that flow took 23 of its 30 seconds. It now waits for the proposal, and e2e tests have 60 seconds. The desktop smoke is now blocking: it passed on every hosted run that reached it. A new check starts two real TomeStack processes on one data folder. It passed three hosted runs in a row, so it is blocking too.

- **CI (M5 stack, 2026-09-29):** the UI flow failed at random steps on the hosted runner (#30, #31 and #35 each had a red run on a commit whose rerun passed), always where a step waited the default 1 second for the DevHost. Every wait in the e2e flow now allows 10 seconds (`e2e/timeouts.setup.ts`); a 200 ms limit reproduced the same failures locally.

- **A second spellcasting class gets its bonuses, with a trace (M2.1; `docs/features/spellcasting.md`):** a bonus to spell attacks or spell save DCs (from an item or a feature) used to reach only the first spellcasting class. A multiclass character's other casters showed a bare proficiency bonus + ability modifier, without saying how it was calculated. Every caster now gets those bonuses, and the Spells panel explains each caster's attack bonus and save DC step by step.

- **One TomeStack per data folder (M2.1; ARCHITECTURE "Data folder"):** starting TomeStack again while it is open now brings the open window to the front instead of opening the same data a second time. Before, the second copy marked the first copy's running PDF import as interrupted, so resuming it could run two imports of one job at once. Its start-up clean-up could also delete a PDF the first copy was still attaching. TomeStack now holds `tomestack.lock` in the data folder while it runs, and Windows releases it when TomeStack exits or crashes. The DevHost is refused on a folder the app has open, and the app on one the DevHost has open.

- **Import review fixes (M4, independent review 2026-09-28; ADR-009, `docs/features/pdf-import.md`):**
  - A page that crashes the worker, runs out of time or memory, or cannot be read by OCR now fails alone: it is marked unreadable and the rest of the book is read. Resuming used to stop on the same page every time. After 5 such pages in one run the import stops, and "Resume" continues after them.
  - What one page can send to the app is now bounded: the character limit covers its blocks and lines too, and the app refuses any worker message longer than a page can hold. The app also checks that the worker really runs under its memory cap before it reads the PDF, watches committed memory as well as the working set, and a worker left behind by a crashed app now exits.
  - Finding candidates holds a bounded amount of text in memory. A job past it detects its first pages and says so in its audit; import the rest as a page range.
  - Cancelling an import, or removing its PDF, now also stops candidate detection.
  - Accepting a candidate saves the draft and marks the candidate accepted together, so a crash cannot lead to a duplicate draft.
  - Importing the same PDF into the same source again no longer proposes entries you already accepted or ignored.
  - A linked PDF that changed on disk is caught when a run starts, not only when it is resumed.
- **Accessibility (import review):** after you accept or ignore a candidate, focus returns to the candidate list instead of being lost, and the final import status ("completed") is announced.
- **Builder choices and spells:** ticking two options quickly (two skills of a choice, or two spells) could drop the first one. Each tick now applies to the latest draft. This also made an end-to-end test flaky.

- **`armor` is content schema v4 only (ADR-003).** A revision stored by 0.2.0 with a `"type": "armor"` effect (an unknown effect then) was read as typed armor. - Original M1 fixtures (`tests/RulesFixtures/fixture-pack-m1.json`, test-only) with a deliberate cross-edition conflict: two different revisions named "Fixture Keen Senses". Side-by-side tests show the same inputs giving different, explained outputs per family (`tests/RulesFixtures/README.md`).
- Dice engine skeleton in the rules core (`docs/features/dice-engine.md`): bounded `NdM±K` expressions, advantage and disadvantage on a single d20, critical dice doubling, a seeded RNG for tests, and a CSPRNG for play. Roll records hold the formula, every die, modifiers with origins, and provenance. Rolling never consumes a resource (SPEC C-04). A request with both advantage and critical doubling is refused rather than silently dropping one. There is no UI yet.
- **Installer (ADR-008, accepted):** a per-user, self-contained, unsigned Velopack installer built by `scripts/pack-installer.ps1`, with `vpk` pinned as a repo-local tool in `.config/dotnet-tools.json`. The pack id is `TomeStack.App`, so uninstalling cannot delete the data folder `%LOCALAPPDATA%\TomeStack`. `LICENSE`, `NOTICE` and `ATTRIBUTION.md` ship next to `TomeStack.exe`. `scripts/installer-smoke.ps1 -Adapter Velopack` proves install → smoke → upgrade from a schema-1 build (with `tomestack.db.v1.bak`) → uninstall that keeps the data, under Windows PowerShell 5.1 and pwsh 7. The version policy is in ADR-008: `Directory.Build.props` is the single source and must go up with every build given to a user. This build is 0.1.1.
- ADR-008 first set out the installer requirements and the options. It records two data-loss risks: Velopack's default install folder is the data folder, and MSIX virtualizes AppData. `scripts/installer-smoke.ps1` is an installer-neutral install → smoke → upgrade → smoke → uninstall harness. Only an Xcopy adapter exists so far.

ADR-007 accepted (D03 and the SRD route: CC-BY-4.0 for both SRDs). The accessibility target is WCAG 2.2 AA for the sheet and builder (D05), and the owner's keyboard walkthrough passed.
- **Backup vs. share export (ADR-007, SPEC P-02, Q-03):** the sheet's export asks what the package is for. A *personal backup* includes everything and is named `…-personal-backup.tomestack.zip`. A *share* leaves out content from non-redistributable sources and lists what it left out before exporting (`package.exportPreview`) and in the manifest (`omitted[]`). The receiver gets a `package.content-omitted` warning naming the source and publisher, and the sheet shows that content as missing.
- **Sync-root warning (ADR-005):** if the data folder is inside OneDrive or another cloud sync root, the app shows a warning at the top of the window (`app.info` `warnings`, code `data-dir.sync-root`).

- **Levels and classes (M1 item 5, SPEC C-01, C-02, C-03; `docs/features/levels-and-classes.md`):** characters record levels per class. The total level is their sum and drives the proficiency bonus. `CLASS_LEVEL` resolves to the level in the class that content belongs to. Grants can apply from a class level (`grant.level`), so a level-3 feature is absent at level 2. New fields, each with a full trace:
  - **Hit points:** the starting class's hit die maximum, then the fixed value per level, plus Constitution × level. Traces cite the class, source and page.
  - **Armor class:** 10 + Dex, with `replace` alternatives; the highest wins.
  - **All 18 skills.**

  Original fixtures "Fixture Warden" and "Fixture Scholar" cover multiclass hit points and level gates. D04 (multiclass and spellcasting scope for MVP) is recorded in LIVING_SPECS.
- **SRD packs (M1 item 1, SPEC S-02, Q-03; ADR-007; `docs/licensing/srd-pack-review.md`):** SRD 5.1 and SRD 5.2.1 ship as two separate CC-BY-4.0 source packs, with separate sources, content IDs and revisions. Each source carries the approved attribution verbatim, a CC-BY §3 `modificationNotice` (which also travels in package notices) and the checked PDF's SHA-256. The slice per family:
  - one species (Half-Orc / Dwarf);
  - one background (Acolyte / Soldier, with its ability options and origin feat);
  - the Barbarian at levels 1–3, with its skill choices, level-gated features and the Path of the Berserker;
  - one feat (Grappler with its Strength 13 prerequisite / Savage Attacker).

  Every revision validates, and `SrdPackTests` checks the attribution against the approval page. `NOTICE` and `ATTRIBUTION.md` carry the statements.
- **Roll command (M1 item 7, SPEC C-04; `docs/features/dice-engine.md`):** `roll` rolls a content roll effect that applies to the character, or a sheet field (ability check, save, skill, initiative) as a d20 test. It returns a roll record with formula, dice, modifiers with their origins, and provenance (revision, source, page). It never changes the character and never spends a linked resource. The sheet now lists its active revisions (`active`).
- **Publishing and pin updates (M1 item 2, SPEC I-06; `docs/features/publishing-and-updates.md`):**
  - `content.saveDraft` stores an inactive draft. `content.publish` re-validates it and inserts a new immutable revision (same content id, new revision id), leaving the draft and older revisions untouched.
  - `content.revisions` lists a content id's history. `content.affected` lists the characters that use it, and how (pin, class, choice, or grant).
  - `character.reviewUpdate` shows the mechanics diff and recalculated fields without changing anything. `character.applyUpdate` moves the character only with an explicit `confirm`, carrying choices over and keeping overrides.
  - An updated character round-trips through a package.
- **Rules-family review for the SRD slice (M1 item 6; `docs/features/rules-family-policy.md`):** the slice needs no new `RulesFamilyPolicy` field. Every difference it exercises is content, or already covered by `AbilityIncreaseSource` and `BackgroundGrantsFeat`. New side-by-side tests use real SRD content: Half-Orc Strength under 2014 vs. 2024 rules, the Soldier's ability option and feat, the Acolyte's feature, and same-named Barbarians never merged. A cross-family exception recorded for a chosen option now admits it too.
- **Restrictions and validation (M1 item 3; `docs/features/validation-and-restrictions.md`):**
  - `restriction` effects are prerequisites. Content whose prerequisite is not met is not applied, with a `restriction.unmet` diagnostic scoped to it. Prerequisites are checked without the content itself, so a feat cannot qualify itself.
  - `content.validate` (`ContentValidator`) reports schema, reference, formula and dependency-cycle problems for a stored or unsaved revision before publish. Errors block publishing; warnings do not.
- **Choices (M1 item 4, SPEC C-01; `docs/features/choices.md`):** characters store selections for `choice` effects. Counts are enforced, and options must be listed and usable under the character's rules family. Every offered choice appears on the sheet, and unresolved ones are flagged ("Choices to make"). Chosen content becomes active with a "chosen from" trace; a chosen subclass follows its class level. `character.choose` records a validated selection. A feature chosen from a species or background follows that origin's ability-increase policy.
- JSON Schemas for source, content revision, character and package manifest (v1, plus v2 for content revisions, characters and manifests) in `docs/schemas/`. A test validates every fixture and a real exported package against them.

### Changed

- The shipped app seeds the bundled SRD packs and **no longer seeds the original test fixtures**. DevHost and tests still do, and `TOMESTACK_DEV_FIXTURES=1` enables them in the shell. Data folders that already have fixture content keep it. The GUI smoke now checks SRD content (a Half-Orc's Strength +2).
- `character.choose` refuses an option that is already selected for another choice (`choice.option-already-chosen`), as SRD wording such as "another skill" requires.

- Trace shape (ARCHITECTURE step 5): a field's trace now includes the steps of every field it reads, in dependency order. Each entry names its `field` and the `inputs` it read, and each value has `units`. Initiative gains an explicit "starts at the Dexterity modifier" step. A field's warnings include its inputs' warnings, so an ignored Dex increase still explains initiative. Overrides stay the final layer, and dependents read the overridden value.
- The ability-increase policy now restricts only *origin* content (species and background). Feats and class features may raise scores under both rules families; M0 blocked them by mistake. For origin content it covers every operation, so a `set` or `replace` on an ability score cannot bypass it.
- The sheet groups its fields and shows each one as an expandable card with its own override form. Override inputs are no longer shared between fields, and derived values no longer use `<output>` (an implicit live region).
- Effect values are formulas. The M0 rule "amount must be between -10 and 10" (`effect.invalid-amount`) is replaced by the formula bounds and `effect.invalid-formula`.
- CI records evidence for the GUI smoke (a WebView2 Runtime probe and the session), runs it through `scripts/smoke.ps1`, adds the missing-runtime check, and uploads the smoke report. The smoke stays non-blocking until it passes on hosted runners (ADR-006). `workflow_dispatch` was added for manual runs.
- Export in the desktop app opens a native Save dialog provided by the shell (`package.saveAs`) instead of WebView2's download flow, which saved silently to Downloads. Browser development against DevHost still falls back to a download (ADR-006).
- D06 resolved: the application service runs in-process behind the WebView2 message bridge instead of as a local ASP.NET Core service. The loopback host is development-only (ADR-006).
- Spec documents moved into `docs/`, and the diagram into `docs/diagrams/`.

### Fixed

- **M1 review (SPEC Q-02, C-03; ADR-004):**
  - Untrusted JSON with empty (null) list entries got an internal error instead of a diagnostic. Examples: `pins: [null]` on `character.save`, `effects: [null]` on `content.validate`, and a packaged character with `pins: [null]` on `package.preview`. Worse, `character.save` stored such a character before failing, and it could not be opened again. Now characters report `character.empty-entry` and revisions `validate.empty-entry` (also on `content.saveDraft` and import), and `character.choose` reports `choice.empty-entry`. `character.save` calculates the sheet before it writes, so nothing is stored on failure.
  - A published revision inside a package was imported without content validation, so, for example, a d1000000 hit die or a choice with count -1 became active. New published revisions in a package are now validated like `content.publish`. For content schema v3, which TomeStack only publishes after validation, errors block the import. Older revisions (published by v0.1, before validation) import with the problems as preview warnings. A reference to content that is missing on this machine is always a warning, because a share package may leave it out. The calculator also isolates such content wherever it comes from: a choice count below 1 (`choice.invalid-count`) and a hit die outside d6–d12 (`class.hit-die-invalid`) are reported, not applied.
  - `RulesFamilyPolicy` could be bypassed through choices and chains. Under SRD 5.1, a background could offer a feat as a choice, or offer a feature that grants one. A background could also grant a feature whose chosen option raised an ability score. Origin (species or background) now carries along any chain of features, so both `BackgroundGrantsFeat` and `AbilityIncreaseSource` hold however the content is reached (`policy.background-feat` now also covers "cannot offer a feat").
- The shell showed an unhandled exception when its UI bundle was missing. It now shows an error and exits cleanly (found by the spike's negative control).
- After an import, the summary (including where the replaced character was backed up) was cleared as soon as the character opened. It now stays visible. Found by the UI flow test.
- In dark mode, error, accent and warning text failed 4.5:1 contrast (2.9, 3.0 and 3.5 to 1). They now use `light-dark()` shades at 7.8 to 10.1 to 1.
- The database backup before a schema upgrade used to copy only `tomestack.db`. In WAL mode, committed data can still be in `tomestack.db-wal` after a crash, so the backup could silently miss it. It now uses SQLite's online backup API (`UpgradeTests`). Opening a data folder from a newer build now shows a clear "update TomeStack" message and changes no data.
- A character or content revision with a `schemaVersion` newer than the build supports used to be accepted silently. It is now refused on import (`package.schema-unsupported`) and on save (`character.schema-unsupported`), and the calculator isolates it (`content.schema-unsupported`).
- Package import used to replace an existing local character after only a preview warning. It now first saves the local copy to `backups/pre-import-*.tomestack.zip`, and importing that file restores it. If the backup cannot be written, the import is refused (SPEC C-07, Q-01; restore test in `PackageRoundTripTests`).
- Package import used to upsert source records, which could silently overwrite local license and redistribution metadata. The preview now shows a field-by-field diff for each differing source, and apply requires an explicit "keep local" or "use imported" choice per source (SPEC S-01, Q-03).
- Exports no longer include a source's `pdfRef`. It is a machine-local path that can contain the Windows user name. Imports never change the local `pdfRef` either.
- Package import bounds the total unpacked size (64 MB, `package.content-too-large`) and checks every entry name before unpacking anything. Before, 2,000 entries of 5 MB each could make a small crafted package exhaust memory. Every package limit and check now has its own test.
- A malformed effect in an imported revision (for example a schema v1 effect without an `id`) failed the import with an internal error. It is now kept as a reference-only effect, and any other reader failure is reported as `package.invalid-json`. v1 effects the v1 build could not have written are no longer mapped with data dropped (ADR-003).
- Export from the desktop app timed out after 30 seconds if the Save dialog stayed open, and reported a failure even though the file was then saved. The UI now waits for the dialog.
- `srd-5.1` blocked every content grant from a background as "cannot grant a feat", including non-feat content such as a background feature.
- Many bounded bonuses on one field could overflow its value (for example, 2,200 bonuses of 500,000 gave initiative −2,094,967,296).
- A dependency cycle also disabled an effect elsewhere in the same component that could not have caused it.
- Derived values always reported `automatic`, even when an effect on them was not applied.
- The UI lint rule caught only a bare `fetch`. It now also blocks `window.fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` and `window.chrome` outside the transport.
- `scripts/smoke.ps1` removes the throwaway data folder the app creates when no `-DataDir` is given.
- The missing-runtime check (`offline-check.ps1 -Mode MissingRuntime`) failed on a hosted GitHub runner: the WebView2 loader ignored `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` there. It now uses a smoke-only shell flag, `--simulate-missing-webview2`, that takes the same not-found path on any machine. It is proven under Windows PowerShell 5.1 and pwsh 7. The loader-override variant stays as a local diagnostic (`-Mode MissingRuntimeLoader`), and the smoke report records which loader overrides the process saw (ADR-006).
- Opening a sheet left keyboard focus on the page body. It now moves to the sheet's heading (WCAG 2.4.3, accessibility checklist #9).
- "New character" did nothing when clicked before the app had loaded its rules families. It is now disabled until then (checklist #11).
- Every commit warned about CRLF line endings. `.gitattributes` now keeps LF in the repository and in working copies.
- Unexpected command failures no longer send the exception message to the UI, because it could contain file paths or internals. The UI gets a generic message and a correlation id. The details (including the stack) go only to `<data dir>/logs/errors.log`, which rolls over at 1 MB (SPEC Q-02).

### Migration

- Database schema v1 (new). Package format v1 (new).
- **Content schema v2 (ADR-003):** effects are a typed union (`modifier`, `grant`, `resource`, `choice`, `restriction`, `recovery`, `roll`). v1 `abilityScoreIncrease` and `initiativeBonus` map to `modifier` bonuses on read. Unknown effect types are kept unchanged (whitespace and escaping normalized) and stay reference-only.
- **Database schema v2:** stored revisions are rewritten in the v2 representation, with new hashes and the original JSON in `legacy_json`. `tomestack.db.v1.bak` is written first. Without this, M0 data folders would have failed to open.
- **Character schema v2:** adds `level` (1–20) and `crossFamilyExceptions`. v1 characters are read as level 1 with no exceptions.
- **Package format v2:** content entries are schema v2. v1 packages still import. Older builds refuse v2 packages with a clear message.
- **Character schema v3:** adds `classes` (levels per class) and `choices` (selections). v1 and v2 characters are read with neither, which changes nothing.
- **Content schema v3 (ADR-003):** adds `grant.level`, `choice.level`, the `hitDie` effect, and the `armorClass` and `hitPoints` targets. v2 revisions are **not** upcast (v2 is a subset of v3), so stored hashes are unchanged and no database migration is needed. v1 still upcasts to v2. Builds that know only v2 refuse v3 revisions.
- Exports now also include content that included content grants (for example class features or a background's feat), so the receiving machine calculates the same sheet. Before, a granted revision that the receiver lacked showed as missing.
- **Package format v3 (ADR-007):** the manifest adds `purpose` (`backup` / `share`) and `omitted[]`. v1 and v2 packages import as backups. Older builds refuse v3. Export file names change: a backup is `<name>-personal-backup.tomestack.zip`.
