# Character import from a D&D Beyond PDF sheet

SPEC C-01, C-06, C-07, P-02, Q-02, Q-03, Q-04, S-03 · ADR-002, ADR-004, ADR-006, ADR-009 · ADR-013 · LIVING_SPECS D16 (decided 2026-10-02, not yet recorded there) · status: **built in slices S0 to S4 and S6 (PRs #57 to #63, not merged); owner decisions taken; reviewed against the code 2026-10-02 (see "Review notes"), S0 findings and review corrections 2026-10-03.** What changed while building is in the LIVING_SPECS change history (2026-10-02 and 2026-10-03 entries). The implementation plan is [ddb-pdf-import-plan.md](ddb-pdf-import-plan.md).

A player who has a character on D&D Beyond exports its sheet as a PDF and turns it into a **new** TomeStack character. They review every match and every number before anything is saved. The import is a one-time move into TomeStack, not a sync.

## What a D&D Beyond PDF is (assumptions S0 must check)

- **A fillable form (AcroForm).** The values sit in named form fields, not only as page text. Reading the fields is exact; reading the page layout is guesswork. **v1 reads form fields only.** A flattened or printed PDF has no fields: the form reader says `ddb.no-form-fields`, and since item 19b `ddb.read` reads such a PDF's page text instead (see "A PDF without form fields").
- **More than one layout.** D&D Beyond has had at least a 2014-style sheet and a 2024-style sheet, and their field names may differ. The importer recognises a layout by its field names, not by text on the page.
- **The library already reads forms.** PdfPig 0.1.16 (already used, Apache-2.0, ADR-009) has, checked in the package's XML docs (`UglyToad.PdfPig.xml`): `PdfDocument.TryGetForm(out AcroForm)` (line 12361), `AcroForm.Fields` (the root fields, 31) and `GetFieldsForPage` (41), `AcroFormExtensions.GetFields` (every field that holds data, 54) and `GetFieldValue` (64), `AcroTextField.Value` (589, null when unset), `AcroCheckboxField.IsChecked` and `CurrentValue` (143-148), `AcroComboBoxField` / `AcroListBoxField.SelectedOptions` (264), `AcroNonTerminalField.Children` (493), `AcroFieldBase.FieldType`, `PageNumber` and `Bounds` (304-324), and `AcroFieldCommonInformation.PartialName`, `AlternateName` and `MappingName` (355-367). **A field's full name is the period-joined chain of its parents' partial names and its own** (355-358), so the reader walks `Children` and builds the full name itself; the maps use full names. `AcroFieldType` (380-430) is `Text`, `Checkbox`, `Checkboxes`, `RadioButton(s)`, `ComboBox`, `ListBox`, `PushButton`, `Signature` or `Unknown`. No new dependency means no new license review.
- **PdfPig cannot write forms.** `PdfDocumentBuilder` has pages, fonts, text, images, bookmarks and link annotations only (`UglyToad.PdfPig.xml` 14357-14560; `AddPageOptions.KeepAnnotation` only copies annotations from an existing document). The fixture generator therefore writes its own minimal PDF (see "Licensing and privacy").
- **Unverified (S0):** whether exports are encrypted or permission-restricted (`pdf.encrypted` is refused today, `PdfPigExtractor.cs:60-63`), whether there is XFA, whether fields are nested (full names with periods), whether checkboxes use `/Yes` or another on-state, how multi-class and subclass are written, whether the sheet marks prepared spells, equipped items and attunement, and how features, spells, attacks and equipment are split across fields (one long text field or many numbered ones). S0 answers all of these; every "layout's rules" below is a map setting, so a wrong assumption costs a map change, not a code change.
- **Most content will not match.** The installed catalog is the two SRDs plus the user's own homebrew, and content breadth is deferred until T2. Anything from a non-SRD book (most subclasses, many species, feats and spells) arrives as **unmatched**. The UI must say so up front, so that a sheet that is 40 % unmatched reads as expected, not broken.

## S0 findings (2026-10-03)

From the owner's one 2014-style export (a single-class character without spells), read through `--ddb-fields`. Counts and kinds of fields only; the inventory itself stays in the gitignored local folder. No 2024-style export has been inventoried yet, so the `ddb-2024` map keeps its placeholder names.

- **Form:** 5 pages, 874 named widget fields (866 text, 7 checkboxes, 1 other) and **no `/AcroForm` in the catalog**; the reader falls back to the pages' widgets (committed, LIVING_SPECS 2026-10-02). Not encrypted (it reads through the worker), no nesting (no full name holds a period). Fields by page: 146, 104, 99, 21, 504.
- **Proficiency marks are text fields,** not checkboxes: one character means proficient, empty means not (`StrProf`, `AcrobaticsProf`, …). The owner confirmed the characters: `P` (proficient) and `E` (expertise, read as proficient; expertise is not imported separately). The map lists them (`markValues`), and any other text is unreadable rather than guessed; the owner's acceptance run passes with exactly these. Of the 7 checkboxes, 6 share the on-state `Yes` and inspiration has its own; a checkbox's state is read from the box, so the on-state does not matter.
- **Classes:** one text field, `CLASS  LEVEL` (two spaces), "Class level" with no subclass. The archetype appears only in the features text, so a 2014 import never fills a subclass from the class field. **Since D16f (2026-10-05)** the Matches step offers the class's subclass choice for any sheet that names no subclass (every 2014 sheet) (see "Matches").
- **Features and feats share text fields** `FeaturesTraits1` to `FeaturesTraits6`: `=== … ===` section headings, `* Name • Source` bullet lines and description lines; feats sit under a `FEATS` heading. The map reads them as one list over numbered fields (`features[n]`) with an item pattern, a section heading and a feats section. Currency fields: owner to confirm the names.
- **Equipment:** rows `Eq Name{n}` and `Eq Qty{n}`, rows 0 to 55 over two pages. **No equipped mark.** Items are created unequipped unless "Equip matched weapons and armour" is ticked (D16g, default on), which equips matched weapons, the first body armour and the first shield.
- **Spells:** `SpellName{n}` and `Prepared{n}`, rows 0 to 49. The prepared mark is mapped as a text mark like the proficiencies but is **unverified** (this export has no spells).
- **Play state:** current and temporary hit points and inspiration are mapped. Death saves are six unnamed checkboxes and are not mapped; there are no fields for spent hit dice or spent slots. All of these stay rested on import.
- **The 2014 map** (`Layouts/ddb-2014.v1.json`, `"unverified": false`) names 79 fields, each checked against the inventory, trailing spaces included. Seven were added on 2026-10-07 (D21, D24): the five coins, `Speed` (read through a pattern that keeps its leading number, so "30 ft. (Walking)" reads 30 and a sheet that starts otherwise is listed as not brought over), and `Passive1`, which the sheet labels passive Perception (`Passive2` and `Passive3` are Insight and Investigation, which the importer does not compare). Unmapped fields, the player name among them, are dropped before the token exists.

**Owner's acceptance run** (`DdbImportAcceptanceTests`, from the local `report.md`; counts, row ids and codes only): layout `ddb-2014`, suggested family `srd-5.1`; name and classes read (1 class); 71 rows (the D16f subclass row included): 14 matched, 1 "Needs a choice" row answered with its first candidate to measure, 52 not found (species, background, `feat:0` and `feat:1`, 38 item rows, 10 feature rows), 5 with no place (`skill:arcana`, `skill:history`, `skill:insight`, `skill:persuasion`, `skill:stealth`, each `skill.no-open-choice`), 0 unreadable; 1 open choice; 36 numbers compared (speed and passive Perception since 2026-10-07; neither differs) with 6 differences (`hitPoints` and the five skills above; Armor Class agrees since D16g's equipping), 6 overrides proposed and **0 differences after them**; every coin reads, so currency is brought over; can apply (re-run 2026-10-07). The low match rate is the expected SRD-only result (see "Most content will not match").

## The fillable 2014 sheet (`wotc-2014`; item 14, Q14, D16(e) amended 2026-10-14)

A second layout, read by the same parser, steps and commands behind the one entry "Import a character (sheet or text)…" (named "Import a character sheet (PDF)…" until the text entry arrived, R133). The report names the layout in words ("D&D Beyond 2014", "D&D Beyond 2024", "the fillable 2014 sheet"); the summary step shows it as "Layout read". No logo or Wizards mark is used; the not-affiliated line stays (D08).

- **Recognition (R72).** A layout is recognised when all its required names are present: `ClassLevel`, `Features and Traits` and `PersonalityTraits ` (trailing space). When several layouts match, the one with the most required names wins only if its set holds every other match's whole set; otherwise the sheet is refused (`ddb.layout-unknown`). The three maps are disjoint, so a doctored file carrying two layouts' names is refused rather than resolved by the order the maps load in. The message no longer says "D&D Beyond".
- **Names are the form's own,** trailing and double spaces included (`Race `, `DEXmod `, `Wpn3 AtkBonus  `). A test pins them in the embedded JSON so a formatter that trims a key fails the build. `PlayerName` is never mapped. The private field inventory stays in the gitignored local folder; this page records names and counts only.
- **Clipping (R78).** The worker reads fields before any layout is known, so it is given `FormLimits.ClipFields`, the union of every layout's `clipFields` (the eight prose fields, `Equipment` and `ProficienciesLang`). A text field in that list over the 20,000-character value limit is cut (never inside a surrogate pair) and flagged `Clipped`, instead of refusing the read; any other field keeps the `ddb.value-too-long` refusal. Both sides check the flag, so a worker that clips a field not in the list, or flags a non-text field, breaks the protocol. The report says "{label} was cut to 20,000 characters.", naming the field, never its text.
- **Ability scores (R95, R97, swap guard).** The sheet has a score box and a modifier box per ability. **Finding:** on the owner's own sheet all six pairs are the other way round from their names: the box named `STR` holds the modifier and `STRmod` the score. The map follows the owner's sheet (`STRmod`, `DEXmod `, `CONmod`, `INTmod`, `WISmod`, `CHamod` are the scores), so a sheet filled that way reads with no report line. A score is still read from whichever box holds it: an unsigned 1 to 30 that agrees with the other box's modifier is the score; if the boxes are the other way round from the map, the score is read from the modifier slot and the report says "{Ability} was read from the modifier box." (one line, "All six ability scores were read from the modifier boxes.", when all six are). A signed number is never a score. A lone box: an unsigned 1 to 30 in the score slot is the score, with no line; a lone value in the modifier slot is the score only when it is unsigned and 11 to 30, with the "read from the modifier box" line. Boxes that disagree, a lone signed number, a lone modifier-slot value of 10 or less, and a number of 31 or more are unreadable, never guessed.
- **Classes.** "Fixture Fighter LVL 5", "Level 5", "lvl. 5" and a bare number all read; several classes are split on "/" and, when that does not read, on commas outside brackets.
- **Hit dice and death saves.** The sheet has a hit dice total ("3d8") and a hit dice left box ("2d8" or "2"). Spent is the total less what is left, as a spent count for that die; a total that is not one die size, a left count above the total or another die is one unreadable field (counted, never guessed), and a blank left box reads nothing. The six death boxes (three successes, then three failures; the order is the form's numbering, not verified against a filled sheet) are counted, and while the order is unverified the report says "Death saves were read as boxes 12 to 14 successes and 15 to 17 failures; check them." whenever any box is ticked **and the play state is brought over** (without that tick the boxes are not brought over, so the preview and the apply leave the line out). Inspiration, spell slots and spells are not mapped.
- **Saves and skills** use the form's boxes (saves are boxes 11 and 18 to 22, skills 23 to 40, in sheet order, so the numbering is not contiguous) and bonus fields; both feed the Numbers step like the other layouts.
- **Weapon rows (R83).** Each of the three rows becomes a custom attack only when its name is 1 to 80 characters and its attack bonus reads (-20 to +30). The damage text is split into dice (through the dice engine, so "200d8" is refused) and a damage type from the closed list (a trailing "damage" is ignored); a part that does not parse is left empty, named in the report ("Weapon row 1: the damage type could not be read and was left empty.") and kept as written in the import note. A row whose name or bonus fails goes to the import note only. A blank row is skipped.
- **Equipment** lines become unequipped custom items: a trailing "(3)" or "x4", or a leading "2 x" or "2x", is the quantity; a bare leading number ("50 ft of rope"), "(0)" and anything else is part of the name; bullets are stripped. Past 50 items, or a name over 80 characters, the line goes to the import note and is counted in the report.
- **Proficiencies and languages** split into the Details page's two lists on "Languages:" and "Tools:" labels (an unlabelled entry goes to tools and other), on commas, semicolons and lines, up to 30 entries of 80 characters; the rest are counted and go to the import note. If reading a line times out, the lines read so far are kept and the unread remainder goes to the import note, counted in the report.
- **Details.** Alignment and the six appearance boxes fill the Details page (a text over 2,000 characters goes to the import note instead).
- **Prose goes to session notes (R79), never to Details.** Personality traits, ideals, bonds, flaws, backstory, features and traits, feats and traits and treasure become one dated note each, titled with the field, in sheet order, split at whitespace into "(part i of n)" notes of at most 4,000 characters. What did not parse or fit is one "Import note" first, so the note limit (200) cuts prose before it; notes that cannot be added are counted in the report. A share package drops session notes, so none of this text is shared; a personal backup keeps it. The "not brought over" list drops notes, backstory, languages, tools and appearance when they were brought over. Allies, experience points, spells, senses and the player name are not brought over.
- **Report lines** are labels and counts only (the tests pin that no sheet text appears in a line, the error log or a message).
- **Reason texts per layout.** A kept number's override reason, the gap note on a noted difference and the text of every import gap note come from the layout: "Imported from D&D Beyond" and "Imported from the character sheet"; "Not brought over from the D&D Beyond sheet: …" and "Not brought over from the character sheet: …". Nothing a fillable-sheet import writes (gap notes, report, stored character) says "D&D Beyond". The Open dialog is titled "Character sheet", and the no-form refusal ("This PDF has no form fields. Save the sheet as a fillable PDF, not printed to PDF.") names no product.
- **Limit on unused boxes.** A box the importer does not use can still refuse the read if it holds more than 20,000 characters, because only the listed free-text fields are clipped.
- **Owner's acceptance** (`WotcSheetLocalTests`, the gitignored local sheet; counts only): 1 sheet recognised as `wotc-2014`; 334 fields; the 111 mapped names are all on the form; 0 unreadable; 1 weapon row to an attack, 12 equipment lines to items, 8 notes, 3 languages, 7 tools and other.

## Behavior

### Flow (the UI)

"Import a character (sheet or text)…" sits in the Characters sidebar (`App.tsx`), next to "Import package…"; the import's title is the same without the ellipsis, and step 1's first line names a fillable sheet PDF, or pasted text or a .txt or .md file (R133). The package button's help text says: "Package import is for TomeStack .zip files. For a character sheet PDF or text, use Import a character (sheet or text)." This fixes the confusion that started this spec.

A step view, not a modal. Each step can go back, and **Cancel at any step writes nothing** (SPEC C-07): it sends `ddb.discard` and returns to the character list.

1. **Choose the PDF.** In the desktop app this is the native Open dialog (`IHostServices.ChooseOpenFile`, `HostServices.cs:19`), so the path never crosses the bridge (ADR-006, as `source.attachPdf` does, `CommandDispatcher.cs:233-239`). In the DevHost and browser, `ddb.read` answers `unsupported` and the UI falls back to a file input and `ddb.readData` (base64, capped; the same fallback `SourcesPanel.tsx:213-225` uses). The result shows: the layout recognised, the character's name, its class-and-level text and counts ("12 features, 9 spells, 14 items read"). Fields the map does not name are dropped here and never leave the service.
2. **Rules and campaign.** Pick the rules family (`srd-5.1` or `srd-5.2.1`) and an optional campaign. The layout suggests one (a 2024-style sheet suggests `srd-5.2.1`), but **the user picks**, and picking the other family shows a warning on this step and in the summary ("This looks like a 2014-style sheet; names will match 2024 content"). The family is never guessed silently (C-01, S-02). A preset for the Numbers step is picked here too (D16h). Whatever the preset, a differing speed row starts as "Keep the sheet's number" (TomeStack's speed is a 30-foot placeholder because some bundled species carry no speed (the M1 Half-Orc and Dwarf), unless the species' content sets one); an explicit row choice still wins.
3. **Matches.** One row per thing read (species, background, each class and its subclass, feats, each proficient skill, spells, items, features), grouped by kind. Each row shows one of:
   - **Matched:** one installed option with the same normalised name, of the right kind and family, published and current. It shows the source and family (S-03). The user can change it.
   - **Choose:** more than one candidate, for example the same name in two sources, or a spell two casters could hold. The user must pick one or "Leave out".
   - **Not found:** nothing installed. It is left out and listed in the report (a gap note under D16b).
   - **No place for it:** installed, but no open choice on the draft offers it and it is not standalone (for example a 2024 general feat: the SRD "Ability Score Improvement" feature is text only, `srd-5.2.1-fighter.json:545-562`, so there is no choice to record a feat in). Left out and listed, like "Not found".
   - **Unreadable:** the field was present but the map could not read it (a level of 25, a quantity of "lots"). Left out and listed.
   - **Subclass (not on the sheet):** when a sheet names no subclass (every 2014 sheet) and the matched class offers its subclass choice at the imported level, a row lists the choice's options (published homebrew included). Exactly one candidate whose every granted feature up to the imported level (a grant with no level counts) appears in the sheet's features is proposed; a name shared with other subclasses is not enough, and candidates with any shared name are listed first (note `subclass.detected-from-features`, or the campaign warning when the source is not allowed); a pick of any published revision of an offered subclass is accepted, one that is not one of the choice's options asks again (`resolution.not-found`); otherwise the row needs a choice or "Leave out", and Create waits for it.
   - Every row has "Leave out". Filters are All, Needs a choice, Not found and Left out. Open choices the sheet does not settle (the 2024 background's ability-score option, a fighting style the sheet does not name) are listed under "Open choices" with their options, unselected; the user may answer them here or leave them for the builder.
4. **Numbers.** A table comparing the sheet and TomeStack for each comparable **calculated field** (`FieldIds`, `Effects.cs:9-46`): the six `ability.<a>.score`, `proficiencyBonus`, `armorClass`, `initiative`, `hitPoints`, the six `save.<a>`, the 18 `skill.<key>`, `spellAttack` and `spellSaveDc`; `spellSlots.<n>` only where the layout maps slots (the 2024 layout does, the 2014 layout has no slot fields). Speed and passive Perception are calculated since 2026-10-06 (D24) and are compared when the layout maps them and the sheet's value reads; otherwise they are listed as not brought over. Differences come first. For each difference the user can:
   - **Use TomeStack's number** (the default);
   - **Keep the sheet's number**, which adds a `FieldOverride(field, value, "Imported from D&D Beyond")` (`Character.cs:258`; the reason is the layout's own, "Imported from the character sheet" for the fillable sheet), shown as an override on the sheet with the computed value beneath it (C-06; `Calculation.cs:497-502`);
   - **Note it**, which makes a `{ kind: "field", fieldId }` gap note after the save.
   There is no "keep all".
5. **Create.** A summary: the name, what will be created (classes and levels, pins, choices, spells, items), how many overrides and gap notes, the play-state checkbox (D16d), and what is not brought over (unmatched and unplaced items, currency unless the layout maps coins and one was read, speed and passive Perception unless the layout maps them, notes, attunement and the rest of D16e, and, unless ticked, play state). If a character with the same name exists (`character.list`), it says so; names are not unique and a second one is allowed. "Create character" saves it. The new sheet then opens, with the import report reachable from it until the app closes.

Accessibility follows [accessibility-checklist.md](accessibility-checklist.md): each step is a labelled region, focus moves to the step heading on every step change, the match and number tables are real tables with row headers, every row's control group is labelled by the row's name, and the status line is a polite live region. The step view is reachable and leavable by keyboard alone.

### Matching rules

- **Name matching is a proposal, never identity** (ADR-002, S-03). Every proposal is shown and can be changed. Nothing is merged by name.
- **Normalisation:** case-folded, trimmed, inner whitespace collapsed, and typographic quotes and dashes folded to ASCII. Source suffixes D&D Beyond adds (a book abbreviation or page, if S0 finds any) are stripped by the layout's rules. Matching is exact on the normalised name. **There is no fuzzy matching in v1**: a near-miss is a wrong match the user may not notice.
- **The search set** is `content.list` for the chosen family and campaign (`TomeStackApp.ListContent`, `TomeStackApp.cs:160-196`): published revisions only, `Compatible` (the family is in the revision's families), not `Superseded` (the newest revision of its content), filtered by kind. With a campaign, an option whose source the campaign does not allow (`AllowedInCampaign == false`) is still a candidate but the row warns; the saved character gets no campaign exception (the sheet's usual warning applies).
- **Where a match goes** depends on the draft, not on the listing alone:
  - A matched option that is one of the **options of an open choice on the draft's calculated sheet** (`CharacterSheet.Choices`, `ChoiceStatus.Options`, `Calculation.cs:64-72`; these include published revisions that extend the choice, `Calculation.cs:1264-1273`) is recorded as a `ChoiceSelection` on that choice. **Skill proficiencies** are matched by the option feature's grant target (`grant: proficiency`, `target: skill.<key>`, for example `srd-5.2.1-classes.json:290-293`), never by name.
  - Otherwise, a `Standalone` option (`ContentOption.Standalone`: no published revision grants it or offers it in a choice, `TomeStackApp.cs:174-177, 192`) becomes a pin, an `EquipmentEntry` or a `KnownSpell` by kind.
  - Otherwise it is "No place for it".
- **Choices are applied in order through the builder's check.** `character.save` validates only the shape of `Choices` (`Character.Validate`, `Character.cs:158-161`); whether a choice is offered, its options and its count are checked only by `WithChoice` (`TomeStackApp.cs:285-319`), which the calculator otherwise reports as `choice.invalid-option` diagnostics on a saved sheet. The importer therefore applies each selection through `WithChoice`, re-calculating between selections, in this order: classes and levels, species, background, subclass choices, then the rest. One option answers one choice (`choice.option-already-chosen`, `TomeStackApp.cs:304-306`): a skill the class and the background both offer is recorded once, on the first choice that offers it. A choice whose level is not reached (`ChoiceEffect.Level`, `Calculation.cs:1250`) is not offered, so a Fighter 2 gets no subclass row.
- **Classes and subclasses:** the class-and-level text (for example "Fighter 5 / Wizard 3") gives `Classes` in the sheet's order. The first entry is the starting class (`Character.cs:43-47`), which matters for saving-throw and skill proficiencies (`onlyAs: startingClass`), and the user can reorder them in step 3; the sheet's order is **unverified** as the order taken. A subclass is recorded as a `ChoiceSelection` on the class revision's subclass choice (for example `choiceId: fighter-subclass`, `srd-5.2.1-fighter.json:317`), found by its options' kind (`Subclass`), never as a pin. A homebrew subclass that extends an SRD class's choice is an option too.
- **Spells:** each spell is matched within the family and attached to one caster: `KnownSpell.Caster` is the content id of the class or subclass whose active `spellcasting` effect the character has (`Character.cs:255`, `CollectCasters`, `Calculation.cs:688-710`). The caster whose `SpellSummary.Lists` names the spell gets it; a spell more than one caster could take, or none, asks the user ("Choose" with every caster). `Prepared` comes from the sheet's prepared mark when the layout has one; cantrips are always `Prepared`, and a known caster's spells too. The same spell under two casters is allowed (`Character.cs:177`); the same spell twice for one caster is recorded once. At most `Character.MaxSpells` (500) are recorded; the rest are listed.
- **Items:** a match plus quantity, and `Equipped` when the layout has an equipped mark; otherwise unequipped, unless D16g's checkbox (Numbers step) is ticked, which fills only items the sheet has no mark for: a mark, equipped or not, always wins. Rows that match the same item are merged into one `EquipmentEntry` with the summed quantity, at most `EquipmentEntry.MaxQuantity` (9,999), since a duplicate is refused on save (`Character.cs:173-176`). An unmatched item is listed with its quantity.
- **Features** granted by the class, species or background are not pinned. They appear by themselves once the class and choices are set. The importer compares the sheet's feature names with the calculated sheet's (`FeatureEntry.Name`, `Calculation.cs:142-151`) and lists any the sheet has but TomeStack lacks as "Not found".

### Ability scores (the one hard calculation)

TomeStack stores **base** scores and derives the final ones; the base is "everything TomeStack does not model". The sheet shows **final** scores. The SRD's level-4, 8, 12, 16 and 19 ability score improvements are **text-only features** in the bundled packs (`srd-5.2.1-fighter.json:545-562`, `effects: []`), so for a character above level 3 the back-solved base rightly absorbs them (a Fighter 8 with 20 Strength from 17 + 2 + 1 gets base 18 under a +2 species bonus, not 17). The 2024 background's ability-score option is a real choice (`features/rules-family-policy.md:30`): it is listed under "Open choices" in step 3, never guessed, and if the user leaves it open the base absorbs those points too; the summary says "answering this choice later raises the score; lower the base by hand then".

The calculator applies modifiers to a score in this order (`ApplyModifiers`, `Calculation.cs:1819-1914`): the highest `replace`, then `bonus` effects with increases before penalties, each increase capped so it never raises the score above `max(20, current)` (`AbilityScoreIncreaseCap`, 1890-1899), then the highest `set`. Modifiers from content the family's `AbilityIncreaseSource` policy refuses are skipped with a warning (1501-1513). So "bonus = calculated − base" is wrong whenever the cap bites or a `replace` or `set` applies. The algorithm, after the matches are resolved:

1. Preview the draft once with every base score at **1** (`character.preview` semantics, nothing stored). For each score read its trace (`DerivedValue.Trace`): if it holds a `replace` or `set` step, the base cannot be solved; propose base = the sheet's score clamped to 1–30 and mark the row "set by <content>". Otherwise sum the `add` steps into `P` (increases, uncapped because 1 + P stays under 20 for any real sheet) and `N` (penalties, never capped).
2. Let `S` be the sheet's score and `T = S − N`. If `T < 20`: base = `T − P`. If `T == 20`: base = `20 − P`, the smallest base consistent with the cap, and the row says "the sheet's 20 may hide a higher base". If `T > 20`: increases give nothing above 20, so base = `T`. Clamp to 1–30; a base outside it is a difference.
3. Preview again with the proposed bases. Every score whose calculated value still differs from the sheet is a difference in step 4, with the trace shown.

A bonus formula that reads another field (`PB`, a modifier) is evaluated at the probe values; step 3 catches the rare case where that changes the sum.

The new service area is `src/AppService/CharacterImport/`. RulesCore is unchanged: the parser is not rules. The file-reading side lives in `src/ImportWorker/Forms/` (the contracts assembly stays `net10.0`).

- **No snapshot is needed:** nothing existing is changed. The owner decision is "snapshots never automatic" (D14).

### Not stored

- The PDF is **not** attached, copied or kept. The temporary file of `ddb.readData` is deleted before the command returns. No content is created, with one exception: the stub class below (item 15) and the reference drafts after it (item 16), the only things an import can put in a source.

### A class TomeStack does not have: the stub class (item 15, D35, ADR-004)

A class row that is "Not found" can be created as a minimal homebrew class for this import, by ticking "Create a homebrew class {name} for this character" in its row (step 3). The class has a hit die and saving throws only: no features, spells or proficiencies. Nothing is written until "Create character"; Cancel at any step writes nothing.

- **When it is offered.** The sheet has a hit dice total, and after taking out each matched class's own die (its levels), exactly one die is left and its count equals the levels of the classes TomeStack lacks. Otherwise the box is held (`aria-disabled`, still focusable) with the reason linked: `stub.hit-die-missing` (no total), `stub.hit-die-unreadable` (not readable, not a d6 to d12, or the counts do not add up). The total is read as groups like `3d10 + 2d8`; the text never appears in an error or the log. **Known limit (R103):** the D&D Beyond layouts map no hit dice total, so their sheets never offer a created class (`stub.hit-die-missing`); it is offered for sheets that carry one, which today is the fillable 2014 sheet.
- **One per import (R100).** Choosing one class holds the others (`stub.one-per-import`: "One class per import can be created here; the others become gap notes."); they stay "Not found" with their gap notes.
- **Saving throws (R101).** The sheet's ticked saves go to the created class only when it is the sheet's first class (TomeStack's rule is that saves come from the starting class). Otherwise the created class has none and the report says "Saving throws come from the first class; the created class has none."
- **The summary shows the class in full:** name, rules family, hit die, saving throws and the source it is saved in. "Publish it" is **unticked by default**. Unticked, it says "The class is a draft: the character gets nothing from it until you publish it in the studio and accept the update on the character." The character is saved with the draft and the calculator isolates it (`content.unpublished`). Publishing the draft in the studio does not change the character: it makes a new published revision, the character is offered the update (`character.updates`), and the class becomes active only when the user reviews and accepts it (R102: characters opt in to every content update). Ticked, the class is published with the character and the character references the published revision.
- **The preview describes the saved character (R129).** `publishClass` is part of the `ddb.preview` request, so ticking or clearing "Publish it" fetches a new preview. The numbers (hit points, saves, the comparison, overrides and gap notes) count the class only when it will be published; unticked they are calculated without it, as the saved character will be, so a number that relies on the class shows as differing. While that preview is loading, "Publish it" and the reference tick are held (`aria-disabled`, still focusable, with the reason linked); after a failed preview they are free again, and "Create character" stays held until a preview succeeds (R142). Each tick has its reason slot beside it, always present and empty unless held, so the reason appearing does not move the focused tick. `ddb.apply` also takes `previewedPublishClass`, the choice of the preview on screen, and refuses with `ddb.publish-changed` when it differs from `publishClass` or is missing while a class is offered (R141). The reference tick changes no number (the drafts have no effects), so it is not part of the preview request.
- **What `ddb.apply` writes**, in one transaction: the source "Characters imported from sheets" (local, import-derived, never redistributable; one per data folder, reused), the draft revision, the publish when ticked, the character. A failure writes none of it. `ddb.preview` and `ddb.apply` take `createClassRow` (a row id); `ddb.apply` also takes `publishClass`. A row that is not offered is refused with `ddb.class-not-offered`. The preview returns `stubOffers[]` and `stub` (the class in full); `ddb.apply` returns `createdClass` (the content id).
- **Never shared.** The source is import-derived, so a character share package leaves the class out and lists it as left out; source packs, campaign packs and "Mark as shareable" refuse it; the sheet JSON and Foundry exports drop it even for a personal copy. A Backup-purpose character export and the library backup are personal and keep it, by design.
- The raw field values live only in memory under the token, and only those the map names. Nothing goes to `import_*` tables, backups or shares.
- What is kept is the character: its pins, choices, spells, equipment, overrides, optional play state and (with D16b) gap notes. These follow the usual rules: a share leaves gap notes out, and a personal backup carries them.

### Reference drafts for unmatched feats and features (item 16, D16(c), R104, R105)

A feat or feature the sheet names, that TomeStack does not have and that carries text on the sheet, becomes one **reference draft**: a draft of the same kind (`feat` or `feature`) holding its name and its description (the revision's summary) and nothing else. It has no effects, so no mechanics. Spells and items are not made into drafts. The drafts live in the same import-derived source as the stub class ("Characters imported from sheets"), so every outbound guard of the stub class applies to them (see "Never shared" above); a personal backup keeps them.

- **Reading the text.** The parser keeps the lines under each list item as that item's text (`FeatureText`: name, kind, text), carried across numbered boxes. `Feats` and `Features` are unchanged. The fillable 2014 sheet's "Features and Traits" is one prose block that goes to session notes, so it yields none.
- **Limits.** A text is cut at 20,000 characters (at a code point) with a report line that names the position ("Feature 3's text was cut to 20,000 characters."), never the name or text. At most 100 drafts per import; the rest are counted ("N more features were left as gap notes."). The gap note stays for every unmatched entry, drafted or not.
- **The summary** lists the drafts (name and first line, the first 10 and "and N more") with the tick "Publish these N reference drafts", **unticked by default** and reset whenever the set shown changes. `ddb.preview` returns `referenceDrafts[]` (row id, kind, name, first line, length); `ddb.apply` takes `publishReferences` and returns `referenceDrafts` (the content ids).
- **What `ddb.apply` writes**, in the same transaction as the character: the drafts, and when ticked one `PublishMany` (confirmed) for all of them. A failure writes none of it; Cancel and discard write nothing.
- **Linking (R105).** A published feat is added to the character's pins, the one place a standalone feat lives. Features are never linked: the character has no slot for a feature that is not granted by a class, species or feat, and none is invented. The summary says "Features are kept as reference content in the studio; the gap notes stay on the character." Unticked, nothing is linked and the drafts stay in the studio.
- **Importing again (R106).** An entry whose kind and normalised name already exist in the import-derived source (any revision, draft or published, whatever its text) is not drafted again, so importing the same sheet twice, or two characters that share a feat, never pile up copies (two published copies would make the next import's match ask to choose between identical entries). Entries repeated within one sheet are drafted once. The report says "N features already had reference drafts and were not added again." (no names); the gap note stays.
- **Positions and names.** A text is matched to its row by position in its list (`feature:2`), not by name, so a left-out first entry cannot lend its text to a same-named second one. A draft's name is cut to 200 characters at a code point, as gap-note labels are.
- **The consent token.** With the publish tick on, `ddb.apply` takes `expectedReferences`, the row ids the summary showed. If the drafts derived at apply differ, or none are given, it refuses with `ddb.references-changed` and writes nothing (the token is kept). Unticked needs none.
- **Campaign.** When a campaign is chosen that does not allow the import-derived source and a feat would be pinned, the preview returns `referenceNote: campaign.source-not-allowed` and the summary says so before Create; the feat is still pinned.
- Names and texts never appear in an error, the log, a code or `ToString`.

### Gap-note schema v2 (D16b): what it costs

- `GapTargetKind` gains `Import` (`GapNotes.cs:7`); `GapTarget` keeps its shape, with `Label` the unmatched name (1 to 200 characters) and `ContentId`, `EffectId` and `FieldId` null; `Validate` (`GapNotes.cs:51-56`) gets the third branch. `AddGapNote` (`gap.add`) **refuses** `import` targets (`gap.target-invalid`: only the importer writes them), and `LabelOf` (161-173) is bypassed for them; `gap.list`, `gap.listAll`, `gap.setStatus` and `gap.delete` work unchanged.
- `GapNote.CurrentSchemaVersion` becomes 2 with an `OnDeserialized` upcast (a v1 note is a valid v2 note unchanged, as `Character` does, `Character.cs:211-215`). `docs/schemas/gap-note.v2.schema.json` (the `kind` enum gains `import`, and a third `oneOf` branch requires `label` alone) and a README row. `SchemaTests` picks the schema by the entry's own version (`SchemaTests.cs:97`), so a v2 note in a backup is checked against v2.
- **Database:** none. Notes are stored as JSON in `gap_notes.json` (`SqliteStore.cs:71-74, 298-301`); the target is inside it.
- **Package format:** no new number. Entry schema bumps have never taken one (character v5 to v7 did not); a backup carrying a v2 note is refused by an older build. **Correction (review, 2026-10-03):** the code is `package.invalid-json`, not `package.schema-unsupported`: `PackageService.cs:901` deserialises the entry before the version check at :903, and `RulesJson` refuses the unknown enum value `import` first. Still refused whole and safely; only the message says "not valid" instead of "update TomeStack". `package-manifest.v9.schema.json` constrains entry paths only (line 42), not the note's version.
- **UI:** `GapTargetKind` in `types.ts:815`, the "About" picker keeps offering features and fields only, the notes list and `PrintView.tsx:258` already render `label`. The sidebar list is unchanged.
- **Exports:** gap notes never reach sheet exports, Foundry files or shares; the restore drill digests the table and needs no change.

## From text (item 19a, D37, ADR-017)

Step 1 also offers "Import a character from text…": a labelled box ("Character text") and a file input (`.txt`, `.md`). `TextSheetParser` turns the text into the same `DdbSheet` the PDF layouts produce (layout id `text`, a synthetic layout outside `LayoutMaps.All`, so no PDF is ever recognised as text), then the hold, matching, numbers, summary and apply are unchanged. No worker is involved, nothing is written to disk, and the text itself is not kept after the token is spent. The steps' header line says so by how the sheet was chosen (a PDF, or pasted or file text, not by the layout read, which can be `text` for a PDF without form fields; R143), once a sheet is chosen: "The PDF itself isn't kept." or "The text itself isn't kept."; before a choice it says "The PDF or text itself isn't kept." (It no longer says "read once": the worker opens a PDF twice when it has no form fields.) The lines that could not be read are the exception, by the user's choice: with "Keep the lines that were not read as session notes" ticked (the default) they become session notes on the character, so they are in backups (not in snapshots or share packages). The step-1 hint says so: "The text itself isn't kept. Lines that can't be read become session notes if you keep the tick." (F6, R131).

**Command.** `ddb.readText { text }` returns the same `{ token, layout, suggestedFamily, summary }` as `ddb.read`, with `summary.notRead` (a count) added. `ddb.preview` and `ddb.apply` take `keepNotRead` (default true); it is part of the request, so the stale-preview hold covers it.

**List caps.** Each list (feats, features, spells) keeps at most `DdbParser.MaxListItems` (1,000) entries; the first one past the cap becomes one unreadable placeholder (so it still gets a gap note) and the rest are dropped. The report counts them, as a number and never a name: "N lines were beyond the 1,000-entry limit of the feats and features lists and were not read." and, for spells, "N spells were beyond the 1,000-entry limit of the spell list and were not read." (the spell line is new; spells used to be dropped after the placeholder with no count).

### A PDF without form fields (item 19b, D37, ADR-013, ADR-017)

`ddb.read` and `ddb.readData` accept a PDF whatever it holds. When the form reader reports `ddb.no-form-fields` (a flattened or printed sheet), the same command reads the page text and gives it to `TextSheetParser`, then returns the same `{ token, layout, suggestedFamily, summary, layoutName }` with layout `text` and layout name "text from the PDF" (the choose step and the summary's "Layout read" row show it). Any other form failure (`pdf.encrypted`, `ddb.too-many-fields`, a worker failure, ...) is reported as before and never falls back. `ddb.readText` stays text only; no PDF travels in a JSON payload.

- **Reading.** The worker's existing `extract` request (ADR-009 (a)) is called from `TomeStackApp` with `PageScope(1, 20)` and the sheet limits (`WorkerFormReader.DefaultLimits`: 20 MB, 50 pages, 30 s). It is the worker's page-text reader (blocks in reading order, OCR when a page has no letters and Windows OCR is installed); it stores nothing, and it does not go through the import-job queue. Measured on the generated text-only fixture (`tests/RulesFixtures/pdf/fixture-text-sheet.pdf`): each printed line comes back as its own line, in page order, so no new request kind was needed (R114). Pages are joined with a blank line.
- **Limits.** Only the first 20 pages are read; a longer document's other pages are counted in one report line ("N pages after the first 20 were not read."). The parser's caps apply to the extracted text (`ddb.text-too-large`, `ddb.text-too-many-lines`, `ddb.text-timeout`), and a page the worker cut short (`page.text-truncated`, `page.blocks-truncated`) is refused as `ddb.text-too-large`, not read in part. A page the worker could not read is counted in a report line.
- **Nothing to read.** Fewer than 10 characters on all the pages (a blank or scanned PDF with no recognised text) is `ddb.pdf-no-text`, with the character and page counts only.
- **Privacy.** Page text is never in a log, message, code or `ToString`; refusals name counts only. Lines the parser did not understand are listed in the summary as for pasted text, as the user's own document.

**The path rule (R116).** Every dialog path the worker reads is checked first by `LocalDrivePath`: a full path on a local drive letter, ending `.pdf`, with no `..`, no network (`\\server\share`) and no device path (`\\?\`, `\\.\`). It applies to `ddb.read` and to `source.attachPdf` (both modes). A refused path is `pdf.path-not-local`, with a message that names no path. A UNC path would make Windows connect to another machine, sending the user's credentials, only to open the file; a relative path would mean whatever sits in the working folder. A drive letter mapped to a network share is not detected. `ddb.readData`'s temporary copy is under the data folder and is not a dialog path.

**Limits (counts only, in every message).** 262,144 UTF-16 characters (`ddb.text-too-large`); 5,000 lines (`ddb.text-too-many-lines`); a line over 2,000 characters is not parsed and is listed as a clipped "Not read" entry; 2 seconds (`ddb.text-timeout`, checked between lines); nothing readable (`ddb.text-empty`). The UI checks `file.size` against the character limit before the file is read and names sizes only. Every regular expression is non-backtracking. Control characters become spaces and a lone surrogate becomes U+FFFD; LF, CRLF and CR all end a line.

**What is read.** Labels (`Name:`; `Class:` with a level or a `Level:` label; `Subclass:`; `Race:` or `Species:`, which suggest the rules family as the PDF layouts do; `Background:`, `Alignment:`, `HP:` as current/max, `AC:`, `Speed:`, `Initiative:`, `Proficiency Bonus:`, `Hit Dice:` or `HD:`, `Passive Perception:`, and age, height, weight, eyes, skin, hair); ability scores in three forms, or six on one line; saves and skills as lists; coins ("15gp 3sp", "Gold: 15"); and headed lists: Spells (with level headings), Equipment, Feats, Features, Languages, Tools. A repeated label is not read twice: the second line is "Not read". A list ends at a blank line followed by a line with no list marker, and that line is "Not read" (so prose after an equipment list is not taken as items). Past 1,000 feat or feature entries, an entry and its description lines are skipped and counted in one report line. Several classes are split on `/` or `,` and need a total of 1 to 20 levels, else the class is unreadable.

**Feats and features** come in two shapes: "Name: description" on one line, or a name with indented or adjacent lines under it (a blank line ends the entry). A bullet starts an item; a comma list gives names only. They fill the same feature lists as the PDF, so unmatched ones become gap notes and reference drafts (item 16) by the same rules.

**Markdown.** Heading marks (`#`), `**` and `__` are stripped, as are list markers (`-`, `*`, a bullet, `1.`, `1)`); rules (`---`) are skipped; a first `# Title` is the name when there is no `Name:` line; a sub-heading inside Features is a feature. Nothing is rendered as markup: text is shown only as plain text, so `<b>` is just characters.

**Reuse.** Equipment lines become your own items, and coins, languages, tools and appearance fill Details, through `ImportExtras` (the 200-note cap counts what it drops); the stub class reads the `Hit Dice` text through `StubClasses.ReadHitDie`; reference drafts read `FeatureTexts`.

**Lines not read.** Every line that no rule understood is kept with its line number (`DdbSheet.NotRead`), listed in the summary as plain text, and, with "Keep the lines that were not read as session notes" ticked (the default), added as session notes titled "Not read from the text (part n of m)" (a single note has no part suffix). Session notes are never in a share package. Unticking drops them, and the report says how many.

**Privacy.** Pasted text is never in a log, error, code or `ToString`; `DdbSheet`, `NotReadLine` and refusals print counts only.

## Architecture

- **Worker.** Reading happens in the existing isolated worker process (`TomeStack.ImportWorker.Host.exe`, JSON lines over stdin and stdout, no socket; ADR-009 (c)). `WorkerRequest` (`WorkerProtocol.cs:11`) gains an optional `Kind` (`extract`, the default when absent, or `formFields`) and `FormLimits`; `WorkerMain` (48-97) answers a `formFields` request with its `worker` line, then one `fields` line `{ fields: [{ name, type, page?, value?, checked?, selected? }] }`, then `done`. The parent side is a new `WorkerFormReader` (`src/ImportWorker/Forms/`) that shares the process start, heap-cap check, bounded line reader, memory watchdog and kill with `WorkerProcessExtractor` (`WorkerProcessExtractor.cs:108-209`) through a small extracted `WorkerSession` helper; it accepts exactly `worker`, `fields`, `done` or `error`, nothing else (`worker.protocol`).
  - The path is the temporary file of `ddb.readData`, or the file chosen in the dialog. It is never a path from the UI (ADR-009). A dialog path is the first file outside the attachments folder the worker reads; ADR-013 records that (the trust is the same as `attachPdf`'s, whose copy is made from the same dialog path).
  - It runs **outside the import-job queue** (`import.busy` is the jobs' own lock, `ImportJobs.cs`): a separate process start, one short call, its own timeouts. The 64 KiB request cap (`WorkerJson.MaxRequestChars`, `WorkerProtocol.cs:29`) holds: the request carries a path and limits, never bytes.
  - The limits are an `ExtractionLimits` with `MaxBytes` 20 MB, `MaxPages` 50, `PageTimeout` and `RunTimeout` 30 s, a sheet-sized heap cap and watchdog (256 MiB managed heap, 512 MiB in all), plus `FormLimits` (`MaxFields` 2,000, `MaxValueChars` 20,000, `MaxTotalValueChars` 1 MB), enforced in the child before anything is sent (PdfPig builds the fields with their values first, so that parse is bounded by the file size and the memory and time caps) and in the parent by the line bound (`MaxMessageChars`: six characters per value character, plus 256 per field, plus 64 KiB).
- **Layout maps are data, not code.** `src/AppService/CharacterImport/Layouts/ddb-<layout>.v1.json` maps full field names to semantic fields (`name`, `classLevels`, `species`, `background`, `abilities.str`, `saves.str.proficient`, `skills.<key>.proficient`, `spells[n].name`, `spells[n].prepared`, `equipment[n].name`, `equipment[n].quantity`, `equipment[n].equipped`, `features`, `play.hitPoints` and so on), with the split rules for multi-value text fields (a separator, or a line pattern) and the layout's checkbox on-state. A layout is recognised when its `required` field names are all present; an unknown layout is refused (`ddb.layout-unknown`), and the refusal reports the count of fields, not their names. The maps are validated at build time by a test (every semantic key known, every regex compiles with its timeout).
  - The maps hold field names only, never D&D Beyond text. Field names are functional identifiers. **They are not rules text, but S0 confirms that before committing them.**
- **Parsing text fields** (the class-and-level string, lists in one field) uses anchored regexes with a short timeout (the detectors use `DetectionLimits.RegexTimeoutMs`, 1 s), or `NonBacktracking`. The parser returns a `DdbSheet` with every value typed or marked unreadable; it never throws on content.
- **Tokens.** The `DdbSheet` cache lives in `TomeStackApp` (`CharacterImport/ImportSessions.cs`): a bounded dictionary (8 live tokens, the oldest dropped first, as `_chosenInputs` does, `CommandDispatcher.cs:330-332`), each with its creation time from `_time` (`TomeStackApp.cs:18`) so expiry is testable, cleared on `Dispose`.
- **UI** calls only `client.ts` (`ddbRead`, `ddbReadData`, `ddbPreview`, `ddbApply`, `ddbDiscard`). New components under `src/Ui/src/components/ddb/`: `DdbImportPanel.tsx` (the steps and state), `DdbMatchesStep.tsx`, `DdbNumbersStep.tsx`, `DdbSummaryStep.tsx`. `fetch` stays in `transport.ts`.

## Limits and malformed input (Q-02, Q-04)

| Input | Result |
| --- | --- |
| Larger than 20 MB, or more than 50 pages | `pdf.too-large` / `pdf.too-many-pages` (a sheet is a few pages, so the caps are far below the book limits of 1 GiB and 5,000 pages, `ImportContracts.cs:53-54`). For `ddb.readData`, 20 MB of base64 is about 27 MB, under the dispatcher's 72 MB request cap (`CommandDispatcher.cs:18`); the decoded length is checked before the temporary file is written |
| More than 2,000 fields, a value over 20,000 characters, or 1 MB of values in total | `ddb.too-many-fields` / `ddb.value-too-long` (the child stops at the limit; a child that sends more fails with `worker.message-too-large`) |
| Not a PDF, unreadable, encrypted with a password | The existing `pdf.not-a-pdf`, `pdf.unreadable`, `pdf.encrypted` (`PdfPigExtractor.cs:41-69`, reused) |
| No form, or XFA only | The form reader says `ddb.no-form-fields`; `ddb.read` then reads the page text instead (see "A PDF without form fields"). If there is almost no text, `ddb.pdf-no-text` |
| A dialog path that is not a full `.pdf` path on a local drive (network, device, relative, `..`) | `pdf.path-not-local`, before the worker or the file is touched |
| Unknown layout | `ddb.layout-unknown` |
| A field the map expects is missing, or a value the map cannot read (a level of 25, a score of "abc", a quantity of 0) | It is not an error. The item is shown as "Unreadable" in step 3 or 4 and left out |
| A sheet whose class levels add up to more than 20, or to 0 | Unreadable classes: the draft gets no classes, step 3 says so, and `ddb.apply` is refused until the user fixes them (`character.level-out-of-range`, `Character.cs:146-157`) |
| Worker crash, memory or a 30-second timeout | `ddb.read-failed` (wrapping the worker code). Nothing is kept, and the temporary file is deleted |
| JavaScript or actions in the PDF | Never run. PdfPig has no script engine (ADR-009). A hostile-input test checks that reading such a file succeeds and does nothing else |
| A second `ddb.read` while a token is live | Allowed; both tokens live until used, discarded, expired or pushed out |

## Licensing and privacy

- **Fixtures must be original** (CONTRIBUTING.md, Q-03). The committed test sheets are generated by a test fixture generator with invented values ("Testy McFixture, Fixture Fighter 3", a homebrew-named species) and use the field names of the maps. Because PdfPig cannot write forms, the generator (`tests/ImportWorker.Tests/FormPdfWriter.cs`) writes a minimal uncompressed PDF by hand: a catalog with `/AcroForm` and `/NeedAppearances true`, one page per sheet page, and one widget annotation per field (`/FT /Tx` with `/T` and `/V`, `/FT /Btn` with `/V` and `/AS` set to the on-state), with a computed xref table. The committed file `tests/RulesFixtures/pdf/fixture-ddb-sheet.pdf` is checked against the generator by a test, as `fixture-import.pdf` is (`ExtractionTests.The_committed_fixture_book_has_exactly_the_generators_original_text`); regenerate with `TOMESTACK_WRITE_FIXTURES=1`.
- **The owner's real PDF stays private**, as with the Stardust Guardian: it goes in the gitignored `tests/RulesFixtures/local/ddb-import/` (`.gitignore:28`; `sheet.pdf`, optional `expectations.json`). `DdbImportAcceptanceTests` skip without it. Their output and `report.md` give only counts and positions, never names or values.
- **No D&D Beyond text enters the repository:** no feature text, no descriptions, no screenshots of their sheet, no field values from a real export. The committed field inventory of S0 lives only in the local folder. The importer reads names and numbers. v1 keeps no feature text at all. Keeping it (D16c) would make an import-derived source, never redistributable, under the existing guards.
- **No network.** The importer does not call D&D Beyond (no character JSON endpoint): the shipped app opens no socket and makes no calls (ADR-006). An unofficial API would also break without notice. The user exports the PDF themselves.
- **No trade dress** (P-03): the review UI is TomeStack's own layout.
- **Personal data:** a sheet may carry a player name. The map does not name that field, so the parser drops it with every other unmapped field before the token is created, and the worker's field list is never stored. Values are never logged (see Commands).

## Risks (what could bite us)

- **The format is not ours and is undocumented.** D&D Beyond can rename fields or change layouts at any time. Mitigations: maps are versioned data, unknown layouts are refused rather than guessed, and S6 re-runs on a fresh export before each release that touches this. A sheet that satisfies two layouts' required names equally is refused as ambiguous, so each real map must require at least one name the other layout's export lacks (the 2024 map, once inventoried, especially).
- **Low match rate.** With SRD-only content most real characters are partly unmatched. The value of v1 is the skeleton plus a precise list of what is missing. The owner should expect that, and it is useful T2 evidence.
- **Overrides can hide calculation bugs.** "Keep the sheet's number" is tempting, and a blanket choice would cover real rule gaps. So it is per field, never "keep all", and each difference can be noted as a gap instead.
- **Subtly wrong matches.** Two sources with the same name are the S-03 case, so the user must pick. There is no fuzzy matching, so a near-miss name stays unmatched rather than being matched wrongly. Importing a 2014 sheet as `srd-5.2.1` matches 2024 content by the same names; the family warning in step 2 is the guard.
- **Base-score back-solve.** The base absorbs every unmodelled increase (ASIs, feats, unmatched species). That is honest, but a later builder answer to an open ability choice double-counts; the summary says so. Every remaining difference is shown.
- **The first character above level 3 may calculate hit points differently** from the sheet (rolled versus average, Constitution changes across levels). The number step shows it; "Keep the sheet's number" on `hitPoints` is the expected answer, and it is one override.
- **Scope creep toward a live sync.** This is a one-time import: no re-import into an existing character, no merging, no network.
- **Roadmap conflict.** It is built before T2 by owner exception (D16a). The exception covers this importer only, not other features waiting on T2.

## Review notes (2026-10-02)

Checked against `main` at 10eef25. What changed and why:

- **Step 4 fields.** Speed and passive Perception were listed; neither is a calculated field (`Calculation.cs:1433`, `FieldIds`, `Effects.cs:9-46`). The comparison now names the exact field ids, and the two go in the "not brought over" list.
- **Creation path.** The spec said "`character.save` path, new id" without saying why not `character.create`. `CreateCharacterRequest` has no overrides, equipment or play state, so `SaveCharacter(Character)` is the only path that carries D16d. Said so, with the line references.
- **Choice validation.** "Through the same check as `character.previewChoice`" was right but under-specified: `Validate` checks the shape of `Choices` only, and only `WithChoice` checks that a choice is offered. Choices are now applied in a stated order through `WithChoice`, and "one option answers one choice" is handled.
- **Ability back-solve.** "Bonus = calculated − base" fails under the 20 cap and under `replace` or `set` (`ApplyModifiers`). Replaced with a probe-at-1 algorithm that reads the trace, with the ambiguity at 20 stated. The SRD ASIs are text-only features, so "an ability-increase choice stays open" was mostly moot; the base absorbs them, and only the 2024 background option is a real choice.
- **Where a match goes.** `Standalone` is "not reachable by any grant or choice", so subclasses, class features, skill options and 2024 feats are never standalone. The rule now routes through the draft's calculated `ChoiceStatus.Options` (which include `extendsChoice` subclasses), matches skills by grant target, and adds the "No place for it" outcome.
- **PdfPig.** `PartialName` is only the leaf; the full name is the parent chain, built by walking `Children`. The field types and the `SelectedOptions` of choice fields are listed. `PdfDocumentBuilder` has no form API, so the fixture is a hand-written PDF (specified) rather than "S1 settles this".
- **Worker.** The request kind, the new message, the shared `WorkerSession`, the temporary-file location and sweep, the `FormLimits`, and why the 64 KiB request cap holds. The dialog path is noted as the worker's first read outside the attachments folder (for ADR-013).
- **Tokens.** Modelled on the dispatcher's `_chosenInputs` (bounded, one use) but kept in the app with `_time` for testable expiry, and cleared on `Dispose`. Unmapped fields (the player name among them) are dropped before the token exists.
- **D16b cost** is now itemised: enum, validation, upcast, schema file, tests, UI type; no database migration and no package format number, with the reason.
- **Edge cases added:** duplicate equipment rows merged (a duplicate is refused on save), the same spell under two casters allowed and under one caster deduplicated, cantrips always prepared, `MaxSpells`, class levels that do not add up, the family-mismatch warning, same-name characters allowed with a notice, attunement and the rest of D16e, serialized commands, hit points above level 3.
- **Limits** reconciled with the existing ones (1 GiB and 5,000 pages per run, 72 MB per request) and the base64 budget shown.
- **UI entry** located (`App.tsx:109-112`), the step view declared non-modal, and the accessibility list made concrete.
