# ADR-016: Assisted class import

Status: accepted (owner decision D34, 2026-10-14; built in Wave 1)
Date: 2026-10-16

## Context

Tester feedback item 11: a detected class page used to end in a class candidate with no effects, so a class had to be rebuilt by hand in the studio. ADR-004 forced every imported effect to `reference`. D34 lets a reviewer confirm the parts of a class that were read from the page, and keeps everything else reference.

## Decision

- **Table reconstruction.** `ClassTableReconstruction` rebuilds a class table from positioned lines: level, proficiency bonus, features, and, for a caster, cantrips, spells known or prepared, and slot columns (or a pact table). It is total (it never throws) and tolerant of rows that wrap. It reproduces the bundled SRD packs cell for cell (`SrdClassTableTests`, which needs the SRD PDFs and skips without them).
- **Proposals, not facts.** `ClassProposals` proposes effects from that table and the class page: hit die, saving throw, armor and weapon proficiencies, a subclass choice (no options), and, for a caster, a `spellcasting` effect. `MulticlassCaster` and `MulticlassTable` are never proposed. The spell list key is the class name, marked unsure until the reviewer saves the candidate.
- **How the traits are read (fix round 1).** A trait is read in both forms the books use: "Label: value" and "Label value" with no colon ("Saving Throw Proficiencies Wisdom and Charisma", "Armor Training Light armor"), and from a two-column trait box, where the label sits alone in its cell and the value (with its wrapped lines) is the cell to its right. A "Core *Class* Traits" box on the page before the class heading is read too: the code reads the labelled lines on the page that carries the class's "Core ... Traits" heading, not strictly only under that heading, so a page with two trait boxes needs the reviewer's per-effect ticks (limiting the read to the lines below the heading is a known follow-up). "All armor" is light, medium and heavy. "None" ends the armor search, so later prose cannot add armor. A weapon line with a condition ("… that have the Light property", "with", "which", "finesse") proposes nothing and says so as an uncertainty, because the effect model has no conditional proficiency. A missing saves, armor or weapons part is an uncertainty ("… were not found on the class page: add them by hand"), never silence. The casting ability is read from the class's text, including up to four following pages (until the next class table) and across a line-break hyphen. Measured on both SRDs in `SrdClassTableTests`.
- **Skills stay a field plus an uncertainty (R69).** The skill line is shown as read and the class carries an uncertainty; no skill `ChoiceEffect` is proposed, because a choice needs installed skill option references per rules family, which the detector does not resolve. The reviewer adds the choice in the studio.
- **Why the class's own `spellcasting` effect is proposed on the class (R52).** Calculation reads a spellcasting effect from any active revision, the class included. A separate feature carrying it would add a link for no gain.
- **Links.** A class links the features its table names: one feature candidate per distinct name; "Ability Score Improvement" and names ending in "feature" are skipped. A name that matches a detected feature of the job links to it. A name that matches **exactly one** installed published feature in the class's rules families, from another source, gets no stub: at accept the class grant pins that published revision (R67, resolved again at accept time from the table, since `grantsCandidates` holds candidates only). A name with two or more such features (for example "Spellcasting" with the SRD installed) or none gets a reference stub, citing the class page, with no effects. A name whose feature was reviewed in an earlier import of the same document is not linked across jobs; the class carries a counted uncertainty instead ("N table features were reviewed in an earlier import and are not linked: add them in the studio", R68). A table name with no linked candidate that, at accept time, has no single installed match (the class's families changed, or a same-name feature was published since detection) is not granted; the check counts these in a note ("N table features are not linked and will not be granted; add them in the studio"), never naming them, and nothing new is pinned. The class stores `grantsCandidates` (candidate id and level) and nothing else is added to the stored candidate (no schema version change).
- **Confirmation at accept.** Every proposed effect has its own "Confirm …" tick, named by the effect, unticked by default; only ticked effects keep `automatic`. Accept as a draft is held until the hit die and, when the class has one, the spell slot table are ticked; the UI says why and keeps focus where it was. A saved edit that changes the effects clears the ticks; one that leaves them as they were keeps them. The kind is the edited one, as the service reads it.
- **Build order.** In one transaction the linked features are saved as drafts first (a pending one is built from its candidate; a stub inherits the class's rules families), then the class draft, whose content grants pin each feature's content id and revision id. A feature already accepted is pinned at its newest published revision, or its newest draft when none is published (so a feature published or re-drafted in the studio after its accept is pinned as it is now). The transaction reads each linked feature's status again and refuses with `candidate.linked-changed`, writing nothing, if one changed since the check. A blocked feature refuses the class with that feature's codes. An ignored one is **not granted** and does not hold the class back; the check says so as a note ("N linked features are ignored and will not be granted", R66). The check returns every link (`linked`: name, level, status, or installed), so the review lists them all however many features the import has.
- **The content grants are automatic, on purpose.** Calculation applies a content grant only when it is automatic; a reference grant would never give the feature. These grants are structural and visible in the list of linked features. The granted features' own effects stay reference, so a linked feature's mechanics still need to be written and published by a person. The grant carries the lowest level at which the table names the feature.
- **Nothing becomes active.** The class and its features are drafts. Publishing is the studio's, with the same validation (ADR-004), and the class and its features can be published together (`content.publishMany`).

## Consequences

- A class page can end in a usable draft after a few ticks, without hand-writing the table.
- Feature stubs add reference-only feature candidates; counts of feature candidates in a book rise accordingly and are not detection recall.
- There is no "un-ignore" command: an ignored linked feature is left out of the class draft (R66); add it in the studio if it was ignored by mistake.
- Linking to one installed feature means a third-party class can grant, for example, an SRD feature of the same name. That is visible in the linked list ("installed") before accepting, and stays inside a draft.
- The SRD 5.1 Sorcerer table is not readable by the reconstruction, so it is a features-only candidate there.

## Alternatives considered

- Making every proposal automatic after one tick: rejected; each automatic effect is a claim about the book that a person must see.
- Reference grants for the linked features: rejected; the calculator ignores them.
- A new stored field for the table: rejected; the proposals carry it (R39).
