# ADR-004: Review before publish for imported content

Status: accepted (contract and enforcement). The publish command, which validates first, is built (M1 item 2); the review UI is M2/M4.
Date: 2026-09-25

## Context

SPEC I-01, I-02 and I-06 and ARCHITECTURE "Import lifecycle": PDF extraction and candidate detection produce **draft candidates, never active rules**. Confidence is a UI hint, never permission to publish. SPEC Q-02 treats every imported document as untrusted.

## Decision

- The import worker can only produce `DraftCandidate`s. `CandidateQuarantine.ToDraftRevision` is the only conversion, and it always yields `status: draft`. Without confirmation every effect is forced to `automation: reference`. No overload or flag produces a published revision. *(Amended 2026-10-16, D34: there is now an overload that takes the effect ids the reviewer confirmed; those keep their automation, every other effect is still forced to reference, and the result is still a draft. The sentence above used to say "no overload or flag"; it now means none that produces a published revision. ADR-016.)*
- Publishing is a separate command (`content.publish`, M1 item 2). It re-runs schema, reference, formula and cycle validation (`ContentValidator`), refuses on any error, and creates a new immutable revision (ADR-002) with a new revision id. The draft is kept unchanged.
- The calculator applies only `published` revisions. Drafts are isolated with a `content.unpublished` diagnostic and never contribute to a trace.
- The same rule holds for packages: drafts inside a package stay drafts and inactive after import. A *published* revision in a package becomes active, so each new one gets the same validation as `content.publish`, shown in the import preview. For content schema v3 (always validated before publishing), errors refuse the import. For older revisions (published by v0.1, before validation existed) they are warnings, and the calculator isolates what it cannot apply (`docs/features/validation-and-restrictions.md`, 2026-09-26 M1 review).
- Imported content never executes code. Effects are declarative data, and formulas use a bounded grammar with no `eval` (ADR-003).
- **M4 D3 (2026-09-28):** `DraftCandidate` also carries `unresolvedReferences`, `fields`, `lowConfidenceFields` and a `summary`. Detection is rule-based (`CandidateDetector`) and stores candidates per import job, locally, for review. It never writes a revision.
- **M4 D4 (2026-09-28): acceptance validates first.** `import.candidate.accept` runs `ContentValidator` on the draft the candidate would become, and refuses on any error. Low-confidence fields and unresolved references block it, until the candidate is edited or accepted as reference only (without its effects). It still yields only a draft (`features/pdf-import.md`).
- **Enforcement fix (M4 D4, found before release):** `ToDraftRevision` now reads the draft back before forcing effects to reference. A candidate held outside a revision carries versioned effect types (spell, weapon, armor) as unknown effects. Setting `automation` on those never reached their JSON, so the stored draft read back with an **automatic** weapon or armor effect. Evidence: `ImportQuarantineTests.A_stored_candidates_versioned_effects_stay_reference_only_in_the_draft_and_after_it_is_read_back`.
- **D33 (2026-10-14): a confirmed preview of the exact drafts is review.** Review used to mean one entry at a time. For many drafts it means this: `content.publishManyPreview` shows each pending draft (newest revision is a draft) with its validation report, the debugger's findings and the re-pointing it needs, writes nothing, and refuses to say "can publish" while any error exists. `content.publishMany` then needs `confirm: true` **and** the pending draft revision ids the preview showed (`expected`); inside its one transaction it re-reads the pending set and refuses with `content.publish-set-changed`, writing nothing, unless the two are equal. A retry or a double press finds nothing pending and writes nothing. Nothing becomes active without a person reading what will be published and confirming it. Everything is all-or-nothing, and published revisions stay insert-only: grants and choice options that pin a draft or an older revision of something published in the batch are re-pointed by saving a new draft and publishing that, never by editing a revision. A draft of a dependent that the request did not name is an error, never swept in. The preview is the real publish run inside a transaction that is rolled back (ruling R50), so it reports what publishing would refuse. **The dependents are bound too (closes the residual of ruling R51, whole-branch review):** the dependents (published content that is re-pointed and published again) are part of what the preview showed, so `content.publishMany` also takes `expectedDependents` (content id to the newest revision id the preview listed). When it is present and the dependents found inside the transaction differ (one added, one removed, or one with a newer revision), the publish is refused with `content.publish-set-changed` and nothing is written; a caller that sends none is not compared. They are still re-checked and validated at publish time. The `affected` list of each `content.publishMany` result is always empty: characters are not counted for a batch, so an empty list means "not computed", not "no character is affected"; each character keeps its pinned revisions until a reviewed update. Bulk accept (`import.candidate.acceptMany`) is the same per-candidate acceptance (provenance, blockers, validation) for up to 200 candidates in one transaction; blocked ones are returned with their codes and never forced. Evidence: `PublishManyTests`, `CandidateReviewTests` (accept many).
- **D34 (2026-10-16): confirmed class effects may stay automatic.** `import.candidate.accept` takes `confirmedEffectIds`, for a class candidate accepted as a draft only. The listed effects keep the automation the detector proposed; all others are reference, as before. The server refuses unknown ids (`candidate.confirm-unknown`), ids on anything but a class draft (`candidate.confirm-unsupported`), and a class without a confirmed hit die or with an unconfirmed spell slot table (`import.class-unconfirmed`). A confirmed effect is still inside a draft: it does nothing until a person publishes the draft in the studio, where it is validated again. `acceptMany` confirms nothing, so it never accepts a class as a draft. **The one exception the service makes itself:** the content grants a class draft carries to its linked features (their new drafts, the drafts or published revisions already accepted, or one installed published feature, R67) are automatic, because the calculator applies a content grant only when it is automatic; they are structural, listed by name in the review, and inside a draft like the rest. The features' own effects stay reference. Evidence: `ClassAcceptTests`, `ImportQuarantineTests.A_confirmed_effect_keeps_its_automation_after_read_back_and_every_other_effect_is_reference`. See ADR-016.
- **D35 (2026-10-14): the import's stub class.** When a character sheet names a class TomeStack does not have, the importer may offer a minimal homebrew class for that one import: a hit die and saving throws, nothing else. It is the same rule as every other import, with the user's confirmation as the review. The class is built in memory and counted as published only inside the preview's calculation (a `DraftOverlayCatalog` that also knows the not-yet-stored source), so the preview shows what the character would get; nothing is written until "Create character". Then `ddb.apply` writes, in one transaction and in this order, the import-derived source ("Characters imported from sheets", local, never redistributable, reused if it exists), the **draft** revision, the publish only if "Publish it" was ticked (the same `PublishMany` as the studio, with `confirm` and the exact draft id, so it re-runs validation and creates a new revision), and the character; a refusal anywhere rolls all of it back. **"Publish it" is unticked by default.** Unticked, the character references the draft and the calculator isolates it with `content.unpublished`, so it gets nothing from the class until a person publishes it in the studio; the summary says so in those words. The hit die is read from the sheet's hit dice total after the matched classes' own dice are taken out, and must leave exactly one die whose count equals the levels of the classes the sheet names that TomeStack lacks; otherwise no class is offered, with a code and no guess. One stub per import (R100); saving throws come from the first class only (R101), otherwise the created class has none and the report says so. A request for a class that was not offered is refused with `ddb.class-not-offered`. The source is import-derived, so the existing guards keep it in: a share package omits it and lists it as left out, source and campaign packs and "Mark as shareable" refuse it, and the sheet and Foundry exports drop it even for a personal copy. A Backup export and the library backup are personal and keep it by design. Evidence: `DdbStubClassTests`.

## Consequences

- Even a 0.99-confidence candidate needs a person to accept it. This is intended.
- The M2/M4 review UI must show the excerpt, the page and the proposed effects, and it must call a publish command that re-validates.

## Alternatives considered

- Auto-publishing above a confidence threshold: rejected by SPEC I-02 and ARCHITECTURE ("confidence is a UI hint").
